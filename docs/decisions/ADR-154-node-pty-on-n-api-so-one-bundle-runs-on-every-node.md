## ADR-154: node-pty on N-API so one bundle runs on every Node

- **Date:** 2026-10-13
- **Decided by:** External contributor, hitting the bug on a fresh `install.sh` run.
- **Context:** `install.sh` verified and installed v0.7.0, then `autonomos install-service` died before the daemon ever came up: `Error: The module '.../pty-55vmey89.node' was compiled against a different Node.js version using NODE_MODULE_VERSION 127. This version of Node.js requires NODE_MODULE_VERSION 141.` Every verb failed the same way, `autonomos status` included, because the wrapper execs `node index.js` and the addon is loaded at import time. The cause was `node-pty@1.0.0`, which is nan-based: it compiles one `build/Release/pty.node` against one `NODE_MODULE_VERSION`, and that number changes with every Node major. `reusable-server-build.yml` pinned Node 22 to make it compile at all ("it does NOT build against Node 25's V8 headers"), so every published tarball carried an ABI-127 binary — while `install.sh` accepted any Node >= 20 and most machines now have a newer one. The two checks disagreed, and the gap was the install experience. The mismatch also bites in reverse: `bun install` on Node 26 can't build 1.0.0 at all, so the repo didn't compile on a current Homebrew Node.
- **Decision:** (1) `node-pty` moves to `1.1.0`, which is built on node-addon-api (N-API). N-API's ABI is stable across Node majors, so one binary loads on Node 20 and on majors that don't exist yet. (2) `build-binary.ts` stages `pty.node` itself. 1.1.0 replaced the static `require('../build/Release/pty.node')` — which bun's bundler saw and emitted as an asset — with `loadNativeModule()`, which builds the path at runtime; bun can't resolve a computed specifier, so it compiles to a bare `__require(...)` and the addon silently leaves the bundle. (3) The bundled loader is patched to try the bundle dir *first*. Its own list probes `../build/Release/` ahead of everything, which reaches outside the install dir. (4) The build asserts on both patch anchors and on the presence of `pty.node`, and refuses to stage for a target that isn't the build host. (5) `ensure-node-pty.sh` looks in `prebuilds/<platform>-<arch>/` as well as `build/Release/`, keeps scanning when a stale store entry has neither, and chmods `spawn-helper` — node-pty's npm tarball ships it mode 644, which fails every spawn on the source path with `posix_spawnp failed.` (6) CI drops the Node 22 pin for `lts/*`, and `install.sh`'s floor is documented as a floor with deliberately no ceiling.
- **Rationale:** The pin and the floor were each locally reasonable and jointly wrong; any fix that keeps a per-ABI binary just moves the version the user must happen to have. N-API removes the coupling at the source rather than negotiating it — the build no longer encodes which Node the user runs, so a Node upgrade can't break an existing install and a release can't be born broken for everyone past the build runner's major. The staging and loader patches are the cost of that upgrade, not incidental: 1.1.0's runtime path resolution is invisible to the bundler, and failing to notice would have shipped a bundle that loads and then can't spawn. Hence the anchor assertions — the 1.0.0 → 1.1.0 bump is exactly the kind of upgrade that silently changes loader shape, and the next one should fail the build loudly instead of reaching users.
- **Alternatives considered:** Pin the wrapper to a Node 22 kept beside the user's own (what unblocked the reporting machine first): refused as a fix — it needs a second toolchain per user, and `autonomos upgrade` overwrites the wrapper. Rebuild node-pty from source at install time: refused, it puts a C++ toolchain (Xcode CLT / build-essential + python3) in the critical path of a curl-to-bash install, and still produces a binary one Node upgrade away from breaking. Add an upper bound to `install.sh`'s check: refused, it converts a crash into a refusal to install and leaves users stranded on whatever Node CI last used. Ship a binary per ABI and select at runtime: refused as a worse version of what N-API already provides. `@lydell/node-pty` (N-API fork with per-platform optional deps): a real option and packaged more cleanly, but upstream `node-pty` reaching N-API in a stable release makes the fork's main advantage redundant, and staying on the canonical dependency is worth more than the packaging.
- **Source:** Contributor bug report and PR, 2026-10-13; reproduced against v0.7.0 on macOS 15 / arm64 with Homebrew Node 26.11.1 (ABI 147).

## ADR-097: Restart reconnects the focused pane's terminal via a reload nonce

- **Date:** 2026-09-09 · **Decided by:** Claude (implementation), reported by Terry
- **Context:** Restarting an agent **while its pane was already focused** left the terminal "just gone" — the user had to click the agent again to get it back. Restarting *from another pane* worked. The #353 fix ended `restartSession` with `switchPane({session, id})` to re-open the pane, but that only remounts the pane when `activePane` actually changes; when you're already on that pane, `switchPane(sameId)` is a no-op.
- **Root cause (a race):** the kill closes the terminal WebSocket (4010) → the keep-alive `LiveTerminal` is marked `ended` + **uncached** but stays glued to the pane showing final output (ADR-072's deferred session-end). Reconnecting needs the pane to re-run `useTerminal`'s attach effect so it re-acquires a fresh terminal (cache-miss → new instance → connects the new PTY). Restart-from-elsewhere gets that remount for free (`activePane` changes). Restart-while-focused depends on the kill's `agent.exited` reconcile retargeting `activePane` *away* before `attach` revives the agent — a race the fast path loses, so the pane never remounts and the dead terminal lingers.
- **Decision:** Make the reconnect **deterministic**, independent of the `activePane` race. Add a per-session `terminalReloadNonce` to the store; `restartSession` bumps it (via `reloadTerminal(id)`) after a successful attach. `useTerminal`'s attach effect depends on the nonce, so a bump re-runs it: its cleanup detaches (and disposes, if `ended`) the old terminal, then it re-acquires a fresh one bound to the restarted PTY. To close the residual window where the 4010 hasn't uncached the old terminal yet (so `acquireTerminal` would return the dying one), the effect calls `disposeTerminal(id)` on a bump **before** acquiring — guarded by a `prevNonceRef` so it fires ONLY on a bump-while-mounted, never on a fresh mount / switch-back (which must keep the ADR-072 cache hit so switching re-streams nothing).
- **Rationale:** The terminal can't distinguish "ended forever" from "ended, about to restart" (both are a 4010), and it deliberately refuses to reconnect an `ended` session — so the restart action must signal the reconnect. Driving it through a store nonce + `useTerminal` deps keeps ownership where it belongs (the hook owns the terminal lifecycle + the container), avoids a store→liveTerminals circular import, and is deterministic rather than timing-dependent. rename (ADR-096) restarts too, so it inherits the reconnect for free.
- **Focus restoration (Terry's re-test):** reconnect alone brings the terminal back but leaves it without keyboard focus — a restart-while-focused pane would render the fresh terminal yet force the user to click back in before typing. So the same reload nonce is also a dep of `useTerminal`'s focus effect: on a bump, if the pane is still active, it re-focuses the just-acquired terminal. `activePane` is unchanged across a restart-while-focused (it was and stays the active session), which is exactly why the isActive-only deps didn't re-fire — the nonce is what tells the focus effect the terminal underneath was replaced. Guarded by `isActive`, so a background restart never steals focus. The raw `terminal.focus()` was replaced with `focusTerminal(sessionId)`, which rAF-polls until the fresh xterm textarea is actually visible (`offsetParent !== null`) before focusing — the `#353` "can't focus what isn't focusable yet" lesson; a raw focus fired the instant the terminal was re-acquired lands on `<body>`.
- **Correction (2026-09-11) — the pane was being CLOSED, not just un-focused.** Live-browser verification of the above (driving the real dashboard, `document.activeElement` as the oracle) showed the reload-nonce/focus fix was necessary but **not sufficient**: on a menu-triggered restart the whole pane dropped to the "Create or select an agent" empty state (`SessionViewManager` renders it on `activePane === null`). Terry's "didn't come back / didn't refocus the pane" was the pane vanishing, not a subtle keyboard-focus miss. The restart's transient-`exited` window (between kill and attach) trips **three** independent snapshot-driven teardown paths, all keying off "id no longer in the live set": (1) **the terminal's WS `onclose` 4010 handler** calls `store.switchPane(null)` when the ended session is the active pane — the primary and immediate one, firing the instant the kill's PTY dies; (2) `applyAgentsSnapshot`'s `pickActiveFallback` retargets `activePane` away; (3) DockviewLayout's `pruneDead` (and the workspace-restore prune) removes the panel. `restartSession`'s closing `switchPane` wins the *first* such snapshot but a poll response already in flight when the kill landed (`agentsPoll` is 5s) resolves late and re-tears-down. **Fix:** a module-level `restartingIds: Set<string>` in the store, added at the top of `restartSession` and held `RESTART_PANE_GUARD_MS` (6s, > the poll interval) past the flow via a `finally`; all three teardown paths skip an id that is mid-restart. The pane now stays put through the restart, the reload nonce reconnects the fresh terminal in place, and the focus effect re-focuses it. A real **Kill** is unaffected (its `killSession` retarget is a direct, ungated `set`). Attach failure drops the guard early so a genuinely-stopped agent's pane still retargets. **Verification caveat:** the `activeElement` focus proof could not be captured via browser automation — the automation tab reports `visibilityState: "hidden"` (occluded window), which freezes `requestAnimationFrame` and nulls every `offsetParent`, so `focusTerminal`'s rAF poll cannot run or succeed in that tab (correct behavior — you can't focus a hidden document). The **pane-stays-open** half was verified directly (screenshots); the focus half rests on `focusTerminal` being the same code path sidebar navigation focuses through in production, now that the fresh terminal is present in the active pane after restart. Guards + lifecycle are unit-tested (`liveTerminals.dom.test.ts`, `store.restartReload.test.ts`). **Review follow-up (nox):** there is a *fourth* teardown path keyed off the same `!liveIds.has()` predicate — `reconcileDeadWorkspaces` (the drag-composed-split binding reconcile) — and the 4010 handler's unconditional `fetchSessions()` means an id-omitting snapshot lands inside the kill→attach window on *every* restart, not only on the racy 5s poll. Left ungated, the guard kept a split's panels alive but let its **workspace binding** dissolve (a 2-member group drops to ≤1 survivor → dissolved + both `dvPaneWorkspace` mappings deleted), so the next click on either member took `syncToActive`'s `ws === undefined` branch and collapsed the split permanently — the inconsistent half my own fix unmasked. Fixed by adding `!restartingIds.has(paneId)` to that predicate too (all four call sites now consistent), mutation-verified in `store.restartReload.test.ts`.
- **Alternatives considered:** **toggle `activePane` through null to force a remount** (rejected — depends on dockview's null-active behavior and a same-tick re-set race); **let an `ended` terminal reconnect when a new PTY appears** (rejected — it can't tell a restart from a true end, and reconnect-on-4010 was intentionally disabled to stop retry-spam on dead sessions); **dispose the cached terminal from `restartSession` directly** (rejected — `store.ts` importing `liveTerminals` is circular; and post-4010 the terminal is uncached, unreachable by id anyway — only the pane's `useTerminal` still holds it).

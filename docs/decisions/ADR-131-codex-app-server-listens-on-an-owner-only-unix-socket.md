## ADR-131: Codex app-server listens on an owner-only unix socket; loopback TCP only as a noticed fallback

- **Date:** 2026-09-30
- **Decided by:** Terry approved fixing the security audit findings; TeamLead approved this design with one change (fall back, don't fail closed); CodexGemini (owner of the Codex transport) reviewed it; SecurityFix-Hardening (agent) built it; SecurityAudit-Claude reviewed.
- **Context:** Security audit V4 (High, the Codex twin's CX-01): each Codex agent's `app-server` daemon listened on `ws://127.0.0.1:<port>` with no authentication, and it runs `danger-full-access`. Any local process of any user could connect, send `initialize`, then `command/exec`, and run commands as the operator. Reproduced live on this branch's base: `{"exitCode":0}` and a marker file written. Codex's `--ws-auth` covers only non-loopback listeners. Browsers were already blocked by an upstream Origin check, which is version-dependent. This was a second control plane outside ADR-055's same-user socket.
- **Decision:**
  1. The daemon listens on `unix://<configDir>/cx/<sha256(agentId)[:12]>-<per-spawn nonce>.sock`; the TUI attaches with `--remote` and `codexControl` with the `ws` package (`ws+unix://`). Measured on codex-cli 0.157.1: that path becomes a symlink to `/tmp/codex-daemon-<uid>/<sha256(PATH)>` (directory 0700, socket 0600), and the protocol is still WebSocket over the socket. The per-spawn nonce matters: measured, a second daemon on the same PATH exits "control socket is already in use" while an orphaned first one keeps it, so a fixed per-agent path made a respawn fail (review of V4). Before choosing, this agent's own stale entries in `cx/` are unlinked (only its own; nothing connects to them).
  2. Readiness is a probe (`codexReadyProbe`), not the output banner, because a unix listener prints none. The socket's real target must be a socket we own, in a directory that is ours, not a symlink, and 0700, and created by THIS spawn (ctime ≥ spawn start). It must accept a connection, and the daemon we started must still be alive. Nothing connects to a socket that fails the check. The daemon's stdout/stderr are drained (an unread pipe blocks its writes), and their tail is quoted in a failed start.
  3. **When unix can't be used, the outcome depends on who could have caused it** (SecurityAudit-Claude's review, approved by TeamLead):
     - *Compatibility* (Codex lacks `--listen unix://`, from an async probe of `app-server --help` cached per path + mtime; or the socket path would exceed sun_path): loopback TCP plus a notice. Honest users hit these, and an attacker can't trigger them.
     - *Hostile* (`/tmp/codex-daemon-<uid>` is a symlink, not a directory, or another user's; or the socket fails verification after start): **refuse that spawn**, never TCP. The notice names the path, the owning uid and the admin fix (`sudo rm -rf …`). Otherwise another local user could pre-create that predictable `/tmp` name and downgrade every Codex agent back to the exec-over-TCP endpoint.
     - *Our own directory, merely loose*: tightened to 0700 in place, and unix is used.
  4. We create `/tmp/codex-daemon-<uid>` 0700 before the first spawn, so another user can't have it ready.
- **Rationale:** A unix socket in an owner-only directory is enforced by the kernel for every client, with no credential to leak or rotate, and Codex supports it natively on both ends. The capability-token alternative (`--ws-auth capability-token`) doesn't apply to loopback listeners in the installed Codex. The fallback is split by cause. Falling back for compatibility keeps TeamLead's rule that an autonomOS upgrade never breaks a working agent. Falling back on a hostile state would turn the fallback into an attacker-controlled downgrade, so those cases refuse instead.
- **Alternatives considered:** (a) `--ws-auth capability-token --ws-token-file`. Rejected: 0.157 applies it to non-loopback listeners only. (b) Fail closed without unix support (the first proposal). Rejected by TeamLead: it breaks every Codex agent for older-Codex users on upgrade. (b2) Fall back to TCP on every failure (the first implementation). Rejected in review: a squatted `/tmp` dir would then force every agent onto the exposed TCP endpoint. (b3) A fixed per-agent socket path. Rejected in review: it collides with an orphaned daemon's socket (measured). (c) The default `unix://` path in `$CODEX_HOME`. Rejected: one fixed name per `CODEX_HOME`, which collides when agents share `~/.codex`. (d) Readiness by the output banner. Impossible: there is none on a unix listener. (e) Trust `/tmp/codex-daemon-<uid>` without checks. Rejected: it is squattable by another local user.
- **Limits:** a same-user process can still connect to the socket, which matches ADR-055's same-user control-plane model. On the compatibility TCP fallback the V4 exposure remains until Codex is upgraded or the path is shortened; the notice says so. The `cx/` sweep removes only stale LINKS: it is not a reaper. An orphaned daemon from a crashed server keeps running and keeps its thread loaded, which makes a resumed Codex agent unable to load that thread. That is pre-existing (reproduced identically on TCP main), and CodexGemini is fixing it with a recorded-pid reaper, which must run before this sweep and match the recorded endpoint. Not measured: whether Codex itself verifies the ownership of `/tmp/codex-daemon-<uid>` (that needs a second uid); our pre-create plus pre- and post-checks don't rely on it.
- **Source:** Security audit phase 1 (SecurityAudit-Claude, V4 / the Codex twin's CX-01); TeamLead's ruling and CodexGemini's transport review over the agent channel; PR for `terry/codex-sidecar-unix-socket`.

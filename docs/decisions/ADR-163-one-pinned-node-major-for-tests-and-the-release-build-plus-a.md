## ADR-163: One pinned Node major for tests and the release build, plus a floor leg

- **Date:** 2026-11-28
- **Decided by:** Terry: the fix as a CI correctness bug, and raising the install floor to 22.22.2 (relayed by TeamLead). The primary version, the floor leg and the guards were chosen by an agent (NodePin) and approved by TeamLead.
- **Context:** The release build (`reusable-server-build.yml`) ran on `node-version: "lts/*"` (ADR-154, part 6), while `test.yml`, `e2e.yml`, `load.yml`, `cli-drift.yml` and `test-install.yml` were each pinned to a literal `"22"`. `lts/*` silently became Node 26 when 26 went Active LTS, the same way `ubuntu-latest` moved under us (#580). So the build ran on one Node and every test on another, and nothing said which was right. Neither was the Node users run. The tarball is a `bun build --target=node` JS bundle that `install.sh`'s wrapper execs with the user's own `node`, floor-only with no ceiling (ADR-154), and node-pty 1.1.0 is N-API, so the build's Node doesn't fix the artifact's ABI. The real risk is behavior that differs by major: #445's Web Storage test passed on a dev Mac's 25 and failed on CI's 22. The floor itself was wrong too. `install.sh` accepted Node 20, but `@sigstore/verify`, `core`, `bundle`, `tuf`, `tuf-js` and `@tufjs/models`, which the release bundles (the server's in-app updater and `verify-provenance.mjs`), declare `engines.node: ^22.22.2 || ^24.15.0 || >=26.0.0`. And the first floor-leg review found the server calls the global `WebSocket` (`gateway/codexControl.ts`), which Node 20 only has behind `--experimental-websocket`. Node 20 itself has been EOL since 2026-04-30.
- **Decision:** (1) `.node-version` (a bare major, `26`) is the one source of truth for the primary Node. Every `actions/setup-node` step reads it with `node-version-file: .node-version`, including the release build. (2) `install.sh`'s `MIN_NODE` becomes the full version `22.22.2`, compared on major.minor.patch (`version_lt`, bash 3.2-safe, base-10 forced), and an older Node is refused with a message saying what to install. (3) A `node-floor` job in `test.yml` runs the server, CLI and scripts node:test suites, real-agent integration included (`make _node-tests`, split out of `_check` so both legs run the same command; the pinned Claude CLI install moved to `scripts/ci-install-claude.sh` so both jobs share one pin), on exactly that version. It READS `MIN_NODE` from `install.sh` at run time and asserts `process.versions.node` equals it, because the runner image has its own node and a setup-node that installed nothing would otherwise go unnoticed. The dashboard's vitest suite stays on the primary only, because the dashboard runs in a browser. (4) `scripts/node-version.test.ts` fails if any setup-node step uses a floating value (`lts/*`, `latest`, `current`, `node`), a literal or matrix version, another version file, both inputs, or none. It also fails if the floor expression appears in a job without its own earlier `floor` step, if `node-floor` is missing or has a job-level `if:`, if the job's own `sed` (executed by the test) doesn't extract `MIN_NODE`, if `MIN_NODE` isn't one full version at or below the primary, and if any package in the bundle's dependency closure (walked from the CLI entry, as installed) has an `engines.node` that excludes `MIN_NODE`. The range matcher is a small subset of npm semver that throws on syntax it doesn't know. It agreed with `semver@7.8.0` on all 924 (version, range) pairs checked: every range in the closure plus edge grammar.
- **Rationale:** 26 is the build's Node already, the current Active LTS (EOL 2029-04), and what a current Homebrew or nodejs.org install gives a user, so it's the closest single stand-in for "what we ship". The floor leg tests the other end of the range `install.sh` accepts, so CI covers both ends instead of one arbitrary point in the middle (22, which was neither). Setting the floor to the bundled dependencies' `engines` minimum means `install.sh` never accepts a Node the code it installs disclaims, and the guard keeps it that way: a dependency bump that narrows its range fails the PR that does it, naming the package. A full-version floor is needed because the narrowing is at the patch level (22.22.1 is excluded). A major-only primary takes the newest patch of 26, so security fixes arrive without a PR, while a new major always needs one. The floor is exact, because it is the oldest Node a user may have. Reading the floor from install.sh rather than copying it keeps the two from disagreeing, which is the failure ADR-154 was about. Evidence before landing, on official Node 22.22.2 locally (integration suites excluded; CI runs them): `make _node-tests` passed 2622 of 2623 tests, and the one failure was this ADR's own guard file, edited while the run was in flight, which then passed on its own (20/20). That run also caught a real break: `git-env-guard.test.ts` read only `_check`'s own lines, so it now follows `$(MAKE) <target>` and still fails when a delegated test line loses `$(GIT_CLEAN_ENV)`. Moving `check` to 26 surfaced a real Node 26 difference on its first CI run: on Linux, Node 26 names its main thread `node-MainThread`, so `ps -o comm` reports that instead of `node`. Only `ptyTerminate.ts`'s straggler log reads `comm` (all process matching uses `args`), so that log stays accurate, and the test that assumed `(node)` now accepts both. Every guard rule was mutation-proven red (floor lowered to 20.20.2 and to 22.22.1, `lts/*` in the release build, `node-floor` skipped, its sed or version assert broken, the floor expression in a job with no floor step, install.sh's compare reduced to the major, its refusal removed).
- **Alternatives considered:** Pin everything to 22: the smallest diff, but it keeps testing a Node that is neither the floor nor what most users run, and 22 goes EOL 2027-04. Keep `lts/*` everywhere: tests and build would agree, but both would move on GitHub's schedule, which is the bug. A full matrix (22/24/26) on every PR: roughly triples the check's cost for little gain over the two ends. A literal `node-version` on the floor job: a second copy of `MIN_NODE` that can drift. `engines` in package.json as the source: nothing installs the bundle through npm, so install.sh is what users hit. Keeping the floor at 20 and fixing the global `WebSocket` uses instead: that fixes one known break and leaves `install.sh` accepting a Node the signed-release verifier's dependencies disclaim. A `semver` dependency for the guard: it would collide with the concurrent all-deps bump. A subset matcher that fails closed was enough. Known gaps, left for follow-up: `autonomos upgrade` and in-app update don't check the Node version, so an existing install on an older Node keeps running there (the changeset tells users); and the sigstore range has holes `install.sh` still accepts (23.x, 24.0 to 24.14, 25.x), since ADR-154 keeps the check floor-only.
- **Source:** autonomOS agent channel, 2026-11-28: TeamLead → NodePin (the brief, then Terry's floor approval), with DepsBump (`@types/node` tracks the floor; it found the sigstore engines). /polish review agents found the global `WebSocket` on Node 20 and the vacuous-green paths the guard now closes.

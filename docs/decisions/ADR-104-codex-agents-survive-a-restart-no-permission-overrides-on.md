## ADR-104: Codex agents survive a restart — no permission overrides on remote resume, a thread pre-flight, and honest mode handling

- **Date:** 2026-09-24 · **Decided by:** Terry ("all fixed"; GO relayed via TeamLead), root-cause + fix by CodexGemini@autonomOS. Implements ADR-100's documented "Option B" and supersedes the Codex resume argv of #237/#257.
- **Context:** On codex 0.154 **no Codex agent survived a server/daemon restart** — forge's v0.7.0 upgrade restart crashed both of its Codex agents, and every isolated repro reproduced it. With #378 (ADR-100) the threads were retained, so nothing was lost, but every resume exited 1 in ~250–650ms. Two independent causes, each confirmed by capturing codex's own error text under node-pty (running the exact argv the runtime uses):
  - **(A) Permission overrides on a remote resume.** `codex resume <thread> --remote <ep>` plus ANY of `-s danger-full-access`, `-c approval_policy=…`, or `--dangerously-bypass-approvals-and-sandbox` → `Error: Permission overrides are not supported when resuming a remote task.` Isolated A/B on one thread and one daemon: each override alone fails, no overrides stays up, and standalone resume (no `--remote`) stays up. The runtime had passed these on the resume path since June, when resume worked, so this is an upstream codex behavior change. It affected every agent in every mode.
  - **(B) Never-prompted threads were never saved.** On 0.154 a prompt-less agent gets a thread within seconds (the 0.144.6 "no thread for minutes" note no longer holds) and we persist it, but codex writes the rollout lazily on the first turn. `codex resume` then fails with `No saved session found`. This is the Codex twin of Claude Code's lazy JSONL, the case ADR-049's `hasResumableSession` handles.
- **Decision:**
  1. **Resume argv carries no permission overrides.** Verified empirically per mode with a real follow-up turn and the rollout's recorded `turn_context`: a resumed thread keeps its creation-time `approval_policy` and `sandbox_policy` exactly (ask/auto/plan → `on-request`, bypass → `never`, sandbox `danger-full-access` throughout). Cross-mode runs proved it keeps them even when the daemon's `-c` says otherwise. Nothing widens or narrows. Fresh spawns still set permissions on both the daemon and the TUI.
  2. **A Codex thread pre-flight (`hasResumableThread`: "does a rollout exist?").** No rollout → nothing was ever saved → clear the thread (in `resolved` and on the record), start a fresh `--remote` thread, and notify with the **full** old thread id. It is **deliberately separate from `hasResumableSession`**, because that hook also arms the onExit force-fresh net, which for Codex would sever a *real* conversation on an environmental resume crash (exactly what (A) was). ADR-100's invariant stands. The probe is **three-state**: found / absent (only when the sessions tree listed cleanly with no match) / **throws** (can't tell → the runtime resumes, failing open). It runs **after the env is final**, against the **agent's** `CODEX_HOME` (a preset or customEnvVar can set its own). The first draft returned "absent" on any I/O error and probed the server's home, so a real thread could be judged unsaved and severed. Both /polish reviewers caught this independently.
  3. **A mode change on resume can't apply to a Codex thread (1 shows the thread keeps its policy), so it is refused honestly** (`resumeCannotApplyModeChange`). The record keeps the mode the process actually runs, the user is told "resumed in X; the switch to Y was not applied; spawn a fresh agent for Y", and it is never recorded as if it took effect. Mode pairs that map to the same Codex policy (ask/plan/auto) are not a change.
  4. **A reattach runs the record's provider** (`resolveSpawnProvider`). Found during validation: `params.provider ?? "claude-code"` ignored the record, so resuming a Codex agent via `POST /api/agents {resumeAgentId}` or `create_agent(resumeSessionId)` without repeating `provider` respawned it as Claude Code **and overwrote the record's provider**, orphaning the conversation (the ADR-061 "collapse undefined too early" class). A contradicting explicit provider is now a 409 `PROVIDER_MISMATCH`.
  3a. **The record follows the thread's REAL mode** (`resumedThreadMode`). A pre-ADR-104 mode-change resume wrote the new mode to the record and then crashed on the override, so the thread still runs the old policy. With overrides dropped, such an agent would run silently wider or narrower than its record. On resume the thread's actual `approval_policy` (its last `turn_context`) is read, and if it disagrees the record is corrected with a notice.
  5. **Codex `auto` is honest.** codex 0.15x accepts only `on-request | never`; our `auto → "on-failure"` was silently coerced to `on-request`, so every Codex auto agent already behaved exactly like ask. Terry's call: keep `on-request` (no widening) but say so, mirroring the `plan` clamp. The mapping is stated explicitly, `unsupportedBy: ["codex"]` (the dashboard shows it n/a, and a stranded pick falls back to ask, its real behavior), the explainer copy is updated, and a user-facing `clampedModeNotice` fires at spawn (plan gets one too). `auto` is clamped to Ask on **both** axes, so the MCP-tool approval mode is `writes` (it was `approve`, which made the "behaves like Ask" claim false in the wider direction; /polish caught it). "Like Ask" is now exact. The clamp notice fires on a fresh spawn, a resume mode change, or a fresh thread from the pre-flight. All user notices on this path are queued and pushed only after the record is written.
  6. **Boot's "✓" means survived.** `resumeActiveAgents` logs "resume started", then ✓ only if the PTY is still alive 5s later (✗ otherwise). The old ✓ printed when `spawn()` returned, before a 300ms resume death.
- **Rationale:** (A) removes flags that are rejected and, as the per-mode `turn_context` evidence shows, redundant on resume. (B) is the smallest pre-flight that proves "nothing to lose" before starting fresh, without re-opening ADR-100's data-loss path. 3–5 follow Terry's rule that silently wider or narrower permissions are worse than a crash: every place a requested mode can't be honored now says so. 4 was a latent data-loss bug on the same path.
- **Alternatives considered:** **resuming then forcing the policy through the daemon** (disproved: a resumed thread ignores the daemon's `-c`); **starting fresh on any resume crash** (re-opens ADR-100's harm: a real conversation severed on an environmental crash); **arming the net via `hasResumableSession` for Codex** (same objection); **auto → never** (widening; Terry declined); **letting a mode change "apply" on the record** (the record would lie about what the process runs).
- **Also found, filed separately:** the graceful-shutdown orphaned sidecar (the 2s SIGKILL backstop is an unref'd timer that can't fire once the server exits) → its own small PR per Terry; a SIGKILL'd server inherently orphans its daemons. And on Claude Code, a turn-less fresh session re-spawned with the same `--session-id` exits 1 on the next resume (A/B confirmed pre-existing on the base commit).
- **Source:** forge v0.7.0 restart crash (ReleaseRollout), OrgChart's audit repro, and the isolated real-codex repros and matrices in this PR's Validation section. Terry's GO and auto decision via TeamLead, 2026-09-24.

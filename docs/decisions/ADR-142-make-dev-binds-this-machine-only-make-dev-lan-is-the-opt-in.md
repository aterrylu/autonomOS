## ADR-142: make dev binds this machine only; make dev-lan is the opt-in

- **Date:** 2026-10-01
- **Decided by:** Terry (human, owner: "make dev: this machine only"), relayed by TeamLead@autonomOS; implemented by SecurityFix-Hardening@autonomOS (agent)
- **Context:** Security audit dependency triage. `make dev` started vite with `--host 0.0.0.0` and a config of `host: "0.0.0.0", allowedHosts: true`. It started the dev API server with no host at all, and `resolveBindHost` returns undefined, which binds every interface. So for as long as a contributor ran `make dev`, anyone on their network could reach the dev dashboard, vite's file serving and its proxy to the API. That vite (6.4.1) also had high-severity dev-server advisories, among them arbitrary file read over its WebSocket. And `allowedHosts: true` accepted any Host header, which is what a DNS-rebinding page needs to reach a dev server even when it's bound to loopback. V9 (#476) had fixed the same exposure in the perf harness only.
- **Decision:** (1) `make dev` binds vite to `DEV_HOST`, default `127.0.0.1`. `make dev-lan` (`DEV_HOST=0.0.0.0`) is the explicit opt-in and prints a warning when it starts. (2) The dev API server always binds `127.0.0.1` (`AUTONOMOS_HOST` set on its command line, which `--env-file` can't override), even under `make dev-lan`: vite proxies `/api`, `/auth` and `/ws` to it, so it never needs the network. (3) `allowedHosts: true` is removed. vite's default (localhost plus raw IPs) covers loopback and LAN-by-IP; a hostname is added with vite's own `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS`. (4) The proxy targets `127.0.0.1`, not `localhost`, which can resolve to `::1` first while the API listens on IPv4 loopback only. (5) vite `^6.4.3`, deduped (vitest had kept a nested 6.4.1). Root `overrides` move fast-uri, qs, path-to-regexp and body-parser past their advisories on every consumer. They arrive with the MCP SDK's express server, which the server never starts, so this is hygiene rather than a reachable fix. All five are lockfile-only entries in `SECURITY_FLOORS` (ADR-137), so a lock refresh can't quietly bring a flagged copy back. (6) `dev-server-loopback.test.ts` pins the expanded `make -n dev` / `make -n dev-lan` commands and the imported vite config.
- **Rationale:** A development server is not a product surface. It should be reachable only by the person running it unless they ask otherwise, and the opt-in should be named and loud rather than a flag they have to know to remove. Keeping the API on loopback even in LAN mode halves what LAN mode exposes at no cost, since everything a browser needs goes through vite's proxy. Verified live: default `make dev` listens on 127.0.0.1 for both processes and is refused from the LAN address, and vite answers a foreign Host header with 403. Under `make dev-lan`, vite listens on all interfaces and is reachable from the LAN while the API is still refused there.
- **Alternatives considered:** Keep `0.0.0.0` and rely on the dev API's token auth: refused, because vite's own file serving and dev-server advisories don't sit behind that token. Bind the API to `DEV_HOST` too: refused as unnecessary exposure. Refresh the transitive packages by deleting their lockfile entries (the V12 technique): measured to re-resolve most of the tree, including a runtime dependency jumping `@anthropic-ai/claude-agent-sdk` 0.2.71 → 0.2.141, so refused. `bun update <pkg>` for transitive packages: it added them as direct root dependencies while the real consumers kept their old nested copies, so refused. Bump esbuild 0.27.3 past its advisory: not reachable (the advisory is about esbuild's own `--serve` dev server, which nothing here runs), and ReleaseRollout's #455 pins esbuild exactly for a reproducible verifier build, so left alone.

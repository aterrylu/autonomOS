## ADR-102: Claude usage says WHY it has no numbers, and reads the `limits[]` window list

- **Date:** 2026-09-24
- **Who:** Terry (bug report + the correction that his work account is a Team plan WITH 5-hour and weekly limits; go on parsing `limits[]` relayed via TeamLead); investigation + implementation by the UsageBars agent, stacked on Performance's async keychain read (#384).
- **Context:** On one of Terry's machines (not accessible to us) the Claude usage bar showed a bare gray "n/a". The code audit showed that exact label renders in ONE branch only: the server answered 200 with no error, not needs-setup, but all four windows empty. Every credential failure rendered something else ("setup needed" / "err" / "delayed" / "–"), and none said why. Terry's home payload (Max plan, one read-only GET) showed the usage endpoint now returns far more than we parse — notably a `limits[]` list (`session` / `weekly_all` / `weekly_scoped` with a model scope) alongside the flat `five_hour` / `seven_day` fields; codexbar decodes `limits[]` too. We only read the flat fields, so an account whose flat fields are null while `limits[]` carries the windows renders precisely the silent "n/a". The Team payload itself has not been captured (no access); the fix is built from the Max shape plus codexbar's decoder, and awaits Terry's `/usage` confirmation.
- **Decision:** (1) **`limits[]` fills slots, flat fields win.** Per slot, the flat field is used when present (every account that rendered before is unchanged — pinned by Terry's real Max payload as a fixture and a live main-vs-branch A/B); `limits[]` fills any slot left null; `weekly_all` claims the overall weekly slot before any scoped entry; a scoped or unknown entry that fits no slot — or a second entry for a slot `limits[]` already filled — becomes a named `extraWindow` (panel row, usage-queue cap, surfaced on the bar only when hottest). Nothing readable is dropped; unreadable entries are logged once. (2) **Every non-happy answer carries a `diagnosis {code, summary, hint, transient}`**, enforced at the single exit (`finalizeAnswer`): OAuth-path causes are classified where they occur (keychain denied / locked from #384's preserved `security` exit code and timeout, credentials file unreadable / malformed, login present but unreadable, API-key or Bedrock/Vertex auth read from Claude Code's config, expired / rejected token, 403, non-JSON or non-object body, network, HTTP status, no window at all); the manual-key path and auto-detect-off get one derived from their existing error. The bar shows a short reason label, the tooltip and panel show summary + hint, and the rotating log gets one line per CHANGE of cause and one on real recovery. (3) **The server alone decides "transient"** — the dashboard only promises "temporarily" / "not your key" when the diagnosis says so. (4) A broken login covered by a saved session key keeps its own reason, so neither failure hides the other.
- **Rationale:** The machine that fails is one we can't inspect, so the product has to explain itself: a reason on the bar turns "it's gray" into a one-line bug report. Flat-first precedence means the new parser cannot change any account that already worked, which is the adjacent-regression risk that matters. Keeping the classifier pure (no keychain, no network) keeps it testable and independent of how the token is read.
- **Alternatives considered:** `limits[]` as the primary source — rejected for now: equal on the Max payload, but it would change working accounts on a shape we have one sample of. Asserting "this plan has no rolling limits" for an empty response — rejected: that was the first hypothesis and Terry refuted it (his Team plan has limits); the no-window hint instead asks for the one observation that separates the cases (`/usage` in Claude Code). Classifying transient-ness twice (server text vs dashboard panel) — rejected after review found a 404 promised "temporarily". Showing spend for spend-billed accounts — not built: `extra_usage` already renders in the panel when enabled.
- **Privacy / auth:** diagnosis inputs are plan LABELS (`organizationType`, `seatTier`) and env var NAMES from Claude Code's own config — never a token, email, or organization name/id (test-pinned). The server's own environment is deliberately not consulted for auth-method hints. Nothing refreshes a token (ADR-048); expired/rejected hints tell the user to run `claude`.
- **Source:** TeamLead@autonomOS relays of Terry (2026-09-24); coordination with Performance@autonomOS (#384); this PR.

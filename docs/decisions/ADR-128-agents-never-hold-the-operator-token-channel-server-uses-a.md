## ADR-128: Agents never hold the operator token: channel server uses a per-agent credential on the internal socket

- **Date:** 2026-09-30
- **Decided by:** Terry approved fixing the security audit findings; TeamLead approved the M variant over the S variant; SecurityFix-Hardening (agent) designed it, with the design challenged and approved by SecurityAudit-Claude before implementation and coordinated with SecurityFix-Auth (who owns the public listener's auth).
- **Context:** Security audit V3 (High): the global operator token was in every agent's argv. Claude Code carried it in its `--mcp-config` JSON and Codex in `-c mcp_servers.autonomos.env.AUTONOMOS_TOKEN=…`, and other local users can read argv (`ps -axww` on macOS, Linux with `hidepid=0`). Codex also logged it. Another local account could then drive the public API as the operator, including spawning a bypass agent. Hardening #7 from the same audit adds a second path: `buildBaseEnv` copied the server's whole env, so a server started with `AUTONOMOS_TOKEN` in its env (the `.env` launch) put the operator token in every agent's process env. The token was only there because the channel server's MCP tools called the public REST API with it.
- **Decision:**
  1. **No agent receives the operator token.** It is removed from Claude Code's `--mcp-config`, Codex's `-c` flags and Gemini's settings file. `buildBaseEnv` strips every inherited `AUTONOMOS_*` key before setting the ones an agent needs. `AUTONOMOS_TOKEN` is a reserved env key, so a preset or `customEnvVars` can't put it back. The statusline uses only the per-agent `/self` path.
  2. **The channel server authenticates with its per-agent token** (the 0600 file from #297), sent as `X-Agent-Session` + `X-Agent-Token`, and makes its REST calls over the **internal Unix socket**, the same 0600 socket the gateway already uses.
  3. **A separate router, `routes/agentApi.ts`, mounted only on the internal app**, holds exactly the method + route pairs the MCP tools call. Each entry forwards to the same router the public API mounts, inside an `AsyncLocalStorage` context that marks the caller as that agent. The public listener's auth is unchanged and never accepts an agent credential.
  4. **Agent-path rules that depend on knowing the caller:** env-preset writes strip secret values server-side (previously only the channel server dropped them, client-side), and every agent write is logged with the agent's name and session.
  5. **`/ws/gateway` upgrade** accepts the per-agent credential, or the operator token as before, so a channel server started before this change keeps connecting until its agent respawns. The register frame still proves identity.
- **Rationale:** This is the audit's M fix over its S fix (moving the operator token into a 0600 file). With S, every agent still holds the operator credential, and the API still can't tell an agent from the human. With M, agents hold only a credential scoped to their own session and to the routes their tools need, and the server can attribute and restrict agent calls. Keeping agent credentials off the public listener leaves SecurityFix-Auth's throttle assumption intact ("public = operator-only") and means no operator-only or dashboard route can be reached with an agent token by construction. The allowlist is a strict Hono router, so the access decision is the router's own match, not a string test on the path that `//`, a trailing slash or an encoded segment could slip past.
- **What this does NOT change, stated plainly:** same-user agents can still read `<configDir>/token` off disk; `AUTONOMOS_CONFIG_DIR` is in their env (ADR-055: the control plane is same-user). What is removed: the cross-uid argv exposure (the V3 vector), the operator token in agents' env and argv, and the server's inability to tell agent calls from the operator's. The capabilities agents already had through their tools are unchanged. The env strip covers the `AUTONOMOS_*` namespace only; it is **not** a general env allowlist, so agents still inherit the rest of the operator's environment (cloud credentials, `CLAUDE_SESSION_COOKIE`, and so on; Hardening #7's broader fix is a product decision left open). An agent can still drop a stored secret by removing its key from `secretKeys`, the same as on the MCP surface today; it can no longer set or blank a secret value.
- **Alternatives considered:** (a) The S fix: the operator token via the 0600 per-agent file. Rejected: it removes the argv exposure but leaves every agent holding the operator credential. (b) Accept the per-agent token on the public listener through the credential seam. Rejected: those routes don't check the caller, so an agent token would unlock operator-level actions there (including env-preset secret writes), and it would break the public throttle's operator-only assumption. (c) Allowlist by path regex in a middleware on the internal app. Rejected in review: a regex can disagree with the router on `//`, trailing slashes, encodings and HEAD, and a wildcard middleware at `/api` would also intercept `/api/hooks`. (d) A full env allowlist for agents. Deferred: it removes things agents legitimately use for development work and needs its own decision.
- **Source:** Security audit phase 1 (SecurityAudit-Claude, V3 and Hardening #7); design review by SecurityAudit-Claude and coordination with SecurityFix-Auth over the agent channel; PR for `terry/agents-without-operator-token`.

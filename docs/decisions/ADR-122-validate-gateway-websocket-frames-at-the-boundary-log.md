## ADR-122: Validate gateway WebSocket frames at the boundary; log unhandled rejections instead of exiting

- **Date:** 2026-09-30
- **Decided by:** Terry approved fixing the security audit findings; SecurityFix-Hardening (agent) chose the shape, reviewed by SecurityAudit-Claude.
- **Context:** Security audit V6: one malformed `/ws/gateway` frame crashed the whole server. `JSON.parse("null")` succeeds and `msg.type` then throws; a `register` without `sessionId` throws on `msg.sessionId.slice` in the rejection log line. The handler is `async`, and `@hono/node-ws` wraps `onMessage` only in a synchronous try/catch, so the throw became an unhandled rejection. The server registered no handler for those, so Node exited and every agent PTY and turn in flight died with it. Every agent can write to that socket (it holds the socket path and a token), including a prompt-injected one. The same shape existed in `codexControl.onMessage` (a non-object frame from the Codex daemon threw on `msg.id` inside a socket listener).
- **Decision:**
  1. Every client→server gateway frame is validated by a Zod schema (`gateway/frames.ts`) before the route reads any field. Only the three types a channel server sends (`register`, `send`, `list_agents_request`) are valid inbound; extra keys are stripped, not rejected, for version skew. A bad frame is dropped and logged by reason only, never by content, because a register carries the agent's credential. A malformed `register` is closed with 1008 (what the channel server treats as "don't reconnect"); a malformed `send` that carries a string `requestId` gets a failed `send_result`, so the sender isn't left waiting out its deadline.
  2. The async `onMessage` body is wrapped in a catch-all, so it cannot reject.
  3. Once the server is up, `run.ts` installs a process-level `unhandledRejection` handler that logs and keeps serving (`processSafetyNet.ts`). It is installed after boot on purpose, so a rejection during boot still fails the boot. `uncaughtException` keeps Node's default (exit, and the service manager restarts).
  4. `codexControl.onMessage` drops non-object JSON frames.
- **Rationale:** Validating at the boundary is the REST pattern already used in `validation.ts` (ADR-078), applied to the one WS surface that parses structured, untrusted input. The catch-all and the process handler are defense in depth for throws nobody has found yet: a rejection is a failed async operation, not corrupted synchronous state, so logging it and continuing is safe, and the cost of the default (killing every agent) is far larger than the cost of a logged bug. An uncaught synchronous exception can leave state half-updated, so it keeps Node's crash-and-restart behavior. The other WS handlers were swept and need no change: `/ws/terminal`'s `onMessage` is synchronous (the library's catch covers it) and its JSON path already null-guards with `parsed?.type`; `/ws/agents` parses no inbound frames; the channel server's client-side parse is already inside a try/catch.
- **Alternatives considered:** (a) Only null-guard the two PoC sites. Rejected: it fixes the reported frames, not the class, and the next field read would reopen it. (b) Close the socket on any malformed frame. Rejected for non-register frames: a single bad `send` from a buggy client would drop that agent's inbound channel, turning a bad message into a lost agent. (c) Also log-and-continue on `uncaughtException`. Rejected: Node documents that the process is in an undefined state after one, and a supervised restart is the safer recovery. (d) Reject unknown keys (`.strict()`). Rejected: it would break a newer channel server that adds an optional field against an older server during an upgrade window.
- **Source:** Security audit phase 1 report (SecurityAudit-Claude, finding V6); PR for `terry/gateway-frame-validation`.

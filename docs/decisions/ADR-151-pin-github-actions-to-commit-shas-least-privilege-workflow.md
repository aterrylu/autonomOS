## ADR-151: Pin GitHub Actions to commit SHAs; least-privilege workflow tokens

- **Date:** 2026-10-08
- **Decided by:** TeamLead@autonomOS (assigned audit finding H4 under Terry's 10-01 approval of the remaining security list); implemented by SecurityFix-Hardening@autonomOS (agent)
- **Context:** Security audit hygiene finding H4. Every third-party GitHub Action except three Pages actions was referenced by a mutable tag (`actions/checkout@v4`, `oven-sh/setup-bun@v2`, `softprops/action-gh-release@v2`, `changesets/action@v1`, …). A tag can be moved to any commit by whoever controls that repo, or by an attacker who compromises it, and the next run executes the new code with this repo's token. That code would include the release workflow, which holds `contents: write`, `id-token: write` and `attestations: write` and signs the build provenance users verify (ADR-126). Five workflows (`test`, `e2e`, `test-install`, `load`, `cli-drift`) also declared no `permissions`, so their scope came from a repository setting rather than the file.
- **Decision:** (1) Every third-party action is pinned to a full 40-character commit SHA, with the exact release in a trailing comment (`uses: actions/checkout@<sha> # v4.4.0`). The SHAs are what each tag pointed to when this landed, so nothing changes behavior. (2) `.github/dependabot.yml` enables weekly Dependabot version updates for the `github-actions` ecosystem only, grouped into one PR. Dependabot moves the SHA and the version comment together, and the PR goes through nox and CI like any change. npm stays out of scope: dependency bumps remain deliberate, behind the lockfile and the security floors (ADR-137). (3) Every workflow declares a top-level `permissions` block. The five that had none now say `contents: read`, the least they need; none writes. Workflows that need more (release, version, decisions-index, site) keep their existing explicit, job-scoped grants. (4) A CI guard (`scripts/actions-pinned.test.ts`) fails if any `uses:` of a third-party action isn't a full SHA with a version comment, or if any workflow lacks a top-level `permissions` block.
- **Rationale:** Pinning by SHA is the only reference GitHub can't move under you, and it is GitHub's own hardening recommendation for third-party actions. Dependabot keeps the pins from going stale, so pinning doesn't trade a supply-chain risk for a stale-dependency one. An explicit `permissions` block makes each workflow's scope readable in the file and independent of a repository-level default someone could change. The repo default is already `read`, so for those five workflows this changes nothing today; it guards against that default changing. The guard makes both properties durable, so a new workflow can't quietly reintroduce a tag reference or an unscoped token.
- **Alternatives considered:** Keep major-version tags and trust the publishers: refused, because a tag is mutable and the release workflow's token is too powerful to hand to whatever a tag points at next. Pin by SHA without Dependabot: refused, because the pins would silently go stale and miss upstream security fixes. Enable Dependabot for npm as well: deferred, because it would open a stream of lockfile PRs, and dependency changes here are deliberately reviewed against the security floors; that's a separate decision. Rely on the repository's default token permission: refused as the only control, since it's invisible in the workflow file and one settings change away from `write`.
- **Source:** Security audit (reconciled SecurityAudit-Codex + SecurityAudit-Claude report), finding H4; TeamLead@autonomOS agent channel, 2026-10-08 (assignment).

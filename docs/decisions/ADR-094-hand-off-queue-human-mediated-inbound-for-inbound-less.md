## ADR-094: Hand-Off Queue — human-mediated inbound for inbound-less agents

- **Date:** 2026-08-29
- **Who:** Terry (design locked via questionnaire; relayed by TeamLead), implementation by the CodexGemini agent. (ADR number is provisional — the later merger takes the next free number; no ADR# is baked into any runtime string.)
- **Context:** Gemini's interactive CLI has no live inbound path (fork ruling A, ADR-064-adjacent: interactive-only, no A2A/headless). The #342 capability guard made a send to such an agent fail loud ("no inbound delivery path"). That is honest but a dead end — there was no way to get a message to a Gemini agent at all. The alternative, injecting into its PTY unattended, was rejected earlier as an unsafe false-ack (no idle gate, no receipt). The unlock: a **human** in the loop dissolves the idle-gate objection — a person delivers at a safe moment — and Gemini emits real hook events (`BeforeAgent → UserPromptSubmit`), so delivery can be genuinely *confirmed*, not assumed.
- **Decision:** A message to a `manual-queue` provider is **queued for human hand-delivery** instead of failing.
  1. **New capability value `messaging.inboundMethod: "manual-queue"`** (Gemini opts in; `inbound` stays `false` — it cannot receive *live*). `"none"` still fails loud. The guard keys on the capability (SSOT), so any future inbound-less runtime is covered without re-arming the bug.
  2. **Sender is fire-and-forget (Q1).** `routeMessage` returns an ACCEPT (`null`, unchanged ADR-064 contract) carrying an optional sender-facing **note** ("accepted — queued for hand-delivery") threaded through an **out-parameter** (`RouteMeta`) — deliberately NOT a widened return type, so the `string | null` contract and its 20+ existing test consumers are untouched. Honest per ADR-064: *accepted*, never *delivered*. No second notification.
  3. **Persisted (Q2)** one JSON file per agent in `$configDir/handoff-queues/` (schedules-store pattern: per-call dir for the #350 guard, 0600 files, shape guard, empty-queue deletes its file). Survives restart.
  4. **Cap 10, reject past it (Q5)** as a *real* failure — distinct from the under-cap accept — so an unattended queue can't grow unbounded.
  5. **Delivery = PTY injection with a hook-correlated receipt.** A trigger (REST today) injects one item via bracketed-paste + Enter; the item leaves the queue **only** when a `UserPromptSubmit` hook confirms submission. One injection in flight per agent (the hook payload has no per-message id, so the next confirming event is the receipt — serialize, don't match); send-all drains one at a time; a 90s timeout releases a stuck lock **without** dropping the message. REST: `GET /:id/queue`, `POST /:id/queue/:itemId/send`, `POST /:id/queue/send-all`, `DELETE /:id/queue/:itemId`.
  6. **Surfacing = a count only (Q3):** `pendingHandoffCount` on the agent surface (derived, not persisted on the record; emitted as an `agent.updated` patch reusing the version) drives a dashboard badge — no status-vocabulary change. Pane controls (Q4): send-one / send-all / discard-one. The **dashboard UI ships in a separate PR** behind Terry's visual gate; this PR is server-only.
  7. **Extensibility directive (design-for, not built):** the delivery TRIGGER is a caller decision, never baked into the queue entry — a human click today, an auto-send mode or a dedicated user-input textbox (whose messages enter this same queue) tomorrow all call the same `injectHandoffItem`. No "queuedByHuman"/"deliveredBy" field on an entry.
  8. **Cleanup:** `deleteAgentRaw` (the single chokepoint every delete path funnels through, where the agent token is already revoked) clears the queue — a deleted agent leaves no orphan file of undelivered messages.
- **Rationale:** The human-in-the-loop reframes a rejected mechanism (PTY injection) as safe: the person is the idle gate, and the Gemini hook is a genuine receipt, so "queued → injected → confirmed" is truthful end to end (the same standard ADR-064 set for live sends). The out-parameter for the note (vs. a discriminated return) kept a load-bearing function's contract and its whole test surface stable — the minimal blast radius. Keeping the trigger separable is what lets auto-send and a text box land later without touching the queue or injection core.
- **Receipt correctness & residual risks (from the /polish review, recorded for Terry):** the receipt is ARMED only *after* the submitting Enter is written, so a `UserPromptSubmit` in the paste→Enter window (a prior turn's late hook, or the human typing) can't be mistaken for the receipt of an unsubmitted message; every dequeue is logged for auditability. Two residuals are accepted for this PR, both bounded and logged, never silent: (1) a stray `UserPromptSubmit` in the brief window *after* the Enter but *before* the injected text's own submit hook would still be taken as the receipt — narrow with single-fire Gemini hooks; full text-correlation is a follow-up gated on verifying the hook payload carries the prompt. (2) If an agent stays busy past the 90s receipt window, the lock is released with the message left queued; a human re-delivering then double-sends if the original actually landed late. The alternative (drop the message on timeout) is worse; the timeout is logged so it isn't invisible. **Both are worth Terry's explicit acceptance before the UI PR makes hand-delivery a routine one-click action.** Queue files are written atomically (temp + rename); a corrupt file degrades the always-on agent list to "no badge for that one agent" (logged, file preserved) rather than 500-ing the whole fleet view.
- **Alternatives considered:** **fail-loud forever** (the #342 status quo — rejected, it's a dead end for Gemini); **unattended auto-injection** (rejected earlier — no idle gate, no receipt = the false-ack ADR-064 exists to prevent; the human restores both); **A2A / headless Gemini** (ruled off the table by Terry — "the whole purpose of autonomOS is CLI coding agents, not event-stream/chatbot"); **widening `routeMessage`'s return to a discriminated union** (rejected — ~23 test edits + rewriting the ADR-064 `null`/`string` idioms in two callers; the out-param is additive and churn-free); **dequeue on injection** (rejected — an unconfirmed paste would silently lose the message; the receipt gate keeps it queued); **a new status label for pending** (rejected per Q3 — a badge, not a status-vocabulary change).
- **Source:** Terry via TeamLead relay 2026-08-29 (questionnaire: Q1 fire-and-forget, Q2 persist, Q3 badge-only, Q4 send-one/all/discard, Q5 cap-10; "BUILD IS GREENLIT … the fleet's flagship build"); design artifact https://claude.ai/code/artifact/e18a3823-b550-4b5f-9bff-6e5afc429493.
- **Refinement (2026-08-30/31, from Terry's live-QA of the dashboard PR #356):** five refinements, surfaced by running AND looking at the real thing:
  1. **Envelope on manual delivery = same contract as automated inbound, with SENDER-KIND-AWARE guidance.** The injected message carries the STANDARD INBOUND ENVELOPE (`formatInbound`: `[from → you via <fromUri>] <body>`) plus a trailing guidance line dispatched on the from_uri SCHEME (ADR-092 semantics), NOT the bare body: an `agent://` sender gets "reply with the autonomos MCP send tool to agent://<name>"; a `schedule://` sender gets "this is a SCHEDULED PROMPT, not an agent, it CANNOT be replied to — just do the task; inspect/change it with get_schedule('<name>')" (the same teaching the router's schedule-reply branch gives, delivered proactively); any other/system scheme gets generic informational wording with NO reply instruction. Table-driven so a new scheme defaults safe, never to the agent wording. **Terry's catch:** a one-size-fits-all "reply to another agent" hint on a schedule-fired prompt is wrong and "wildly confusing" — the schedule is not an agent and has no reply path. A hand-delivered paste lacks the `<channel>` framing a live inbound carries, so this guidance is what teaches the recipient how to treat it. The queue entry stores `fromUri`; the pane PREVIEW shows sender + body only (envelope is injection-only) and visually distinguishes kinds ("Schedule · <name>" chip vs a plain agent name); receipt correlation keys on the next confirming event (not text-match), so the longer injected string doesn't affect it. **Format (Terry, later same day):** the envelope is a COMPACT single line — header immediately followed by the guidance in parens, then the body: `[from → you via <uri>](<kind-aware guidance>)\n<body>` — the earlier multi-line form wrapped ugly.
  2. **Derived agent fields must be enriched at BOTH serialization boundaries.** The dashboard sidebar reads agents from the `/ws/agents` RECONCILE snapshot, not `GET /api/agents` — enriching only the REST list left the pending badge absent on a fresh load with a pre-existing queue (it appeared only after the next live delta). Fixed with a shared `withPendingHandoffCount` enricher applied to both. Mocked-store unit tests can't catch this class; the live pass did.
  3. **Send-all is ONE batched injection, not a one-at-a-time drain (Terry).** `injectAllHandoffs` composes EVERY queued message's envelope into a single paste with one Enter; a single receipt dequeues the whole batch — all-or-nothing (if it doesn't confirm, none are dequeued, no partial-delivery ambiguity). Per-message Send is unchanged. The in-flight entry tracks the item id LIST so the receipt knows which items the injection covered.
  4. **User-visible name = "Incoming messages", with ACTION-CARRYING copy (Terry, 2026-08-30).** The feature's internal name stays `handoff-` everywhere it doesn't show — component (`HandoffOverlay`), types (`HandoffQueueItem`), REST endpoints (`/:id/queue`), the `pendingHandoffCount` field, test ids. Only the strings a human reads change: the overlay TITLE is **"Incoming messages"** (the name says WHAT it is); the badge tooltip and the overlay SUBTITLE are **"N awaiting your delivery"** (the copy says WHAT TO DO); the per-item action is **"Deliver to this agent"** (was "Send") and the footer is **"Deliver all →"** (was "Send all →"). **Rationale:** Terry rejected "Inbox" — an inbox is a passive receptacle, but this queue demands an action from the operator (it is inbound-*less* precisely because delivery is manual), so every string is imperative and framed around the human's delivery act. Separating the noun (name) from the verb (copy) keeps the surface honest: the panel is named for its contents, the words tell the operator they are the delivery mechanism. The internal/external split (ADR records the mapping) means the rename touched zero identifiers, endpoints, or persisted shapes — pure UI-copy, no migration.
  5. **Overlay separation = original surface + hairline + glow (Terry’s live pick + refine).** `--card` equals `--background` (#0a0e14), so the floating panel had no edge against the pane (worst over a pure-black region). A comparison-mockup artifact rendered the REAL overlay in five treatments; Terry picked E (elevated surface + hairline + glow) then refined it live — dropped the lighter surface ("a different panel color looks really ugly"), keeping a 1px hairline + a whisper glow. Shipped as a SHARED token family (`--overlay-surface`/`--overlay-hairline`/`--overlay-divider`/`--overlay-glow` in index.css) referenced by BOTH floating overlays — Incoming messages AND the usage-queue auto-Enter control — so they stay one visual family and a restyle is one value change. The usage overlay KEEPS its own accent border (armed/off STATE), joining only the surface+glow. The hairline tracks `--foreground` at low alpha so it survives a light theme.

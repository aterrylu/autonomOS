## ADR-144: Env-preset allowlist covers every documented provider; operator extra keys; refuse unknown keys

- **Date:** 2026-10-02
- **Decided by:** TeamLead@autonomOS (scope, and the refuse-at-spawn ruling), on Terry's report; implemented by SecurityFix-Hardening@autonomOS (agent)
- **Supersedes:** ADR-143 (its built-in key list, and its "skip and notify" handling of keys off the list; the allowlist principle stands)
- **Context:** ADR-143 (#496) limited env presets to an allowlist of model-backend keys, but built the list from autonomOS's own docs ("the documented kimi shape": base URL, model, auth token) instead of the providers' setup guides. Terry found it on another deployment: his Kimi presets for Claude Code set keys the list didn't have, so after the upgrade they couldn't be saved, and their agents would have started without them. Moonshot's official Claude Code guides (international and CN) set `ANTHROPIC_DEFAULT_FABLE_MODEL`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_CODE_EFFORT_LEVEL`, none of which were listed. A preset missing a model-routing key doesn't fail loudly: the agent can quietly run a different model, so ADR-143's "skip and notify" produced exactly the half-working agent an upgrade must never create.
- **Decision:** (1) The built-in allowlist is rebuilt from PRIMARY sources: Claude Code's environment-variable reference (code.claude.com/docs/en/env-vars, plus its Bedrock, Vertex, Foundry and network pages), the official Claude Code guides of Kimi/Moonshot (both platforms and Kimi Code), Z.ai and BigModel GLM, DeepSeek, OpenRouter, LiteLLM, Alibaba DashScope, MiniMax, Vercel AI Gateway, Requesty and Cloudflare AI Gateway, and the Codex and Gemini CLI references. It holds every documented key that selects a model, endpoint or credential, or tunes requests (timeouts, effort, context window, caching, gateway discovery, telemetry opt-outs), plus proxy, CA trust and client certificates. `VERTEX_REGION_CLAUDE_*` is allowed by prefix. Empty values are accepted (OpenRouter and Vercel set `ANTHROPIC_API_KEY=""` on purpose). (2) `NEVER_PRESET_KEYS` lists the keys no preset may set under any setting, because they make a CLI run code or load its config, plugins, hooks or credentials from elsewhere. That covers shell and shell-prefix variables, `CLAUDE_CODE_PROCESS_WRAPPER`, `CLAUDE_ENV_FILE`, plugin and config directories, `AWS_CONFIG_FILE` (whose `credential_process` runs a command), `CODEX_HOME`, `GEMINI_CLI_HOME`, Gemini's sandbox command and system-prompt file, git and runtime injection variables, and the loader variables. (3) An operator-only escape hatch, `envPresetExtraKeys` in settings (dashboard: Settings → Env presets → "Extra allowed keys", with an explicit confirm to add a key), adds keys for a provider autonomOS doesn't know yet. It can't add a control-plane key or a `NEVER_PRESET_KEYS` key, which the route refuses and `isAllowedPresetKey` ignores even if written straight to settings.json. Agents can't change it: the settings route isn't on the agent API (ADR-129, pinned in agent-api.test.ts), and agents don't hold the operator token. (4) A preset that sets a key off the list (built-in plus extra) REFUSES to spawn, with a message naming each key and the fix: allow it in Settings, or remove it from the preset. A fresh spawn returns 422. A boot resume or restart surfaces the message as the dashboard warning those paths already push. (5) A CI table (`env-preset-providers.test.ts`) holds each provider guide's exact variable set, each with its source URL. Every one must be accepted and inject in full, and dropping any of its keys from the allowlist turns it RED, naming the provider.
- **Rationale:** An allowlist is only as good as the evidence it's built from. ADR-143 was right to refuse anything that can run code, but wrong about where the line between "configures a backend" and "everything else" falls, because nobody read the providers' guides. Citing each guide in a test makes the list falsifiable: a provider guide that adds a key is one fixture row, and the test then says exactly what to add. Refusing beats skipping, because a skipped routing key fails silently while a refused spawn fails loudly with the fix. Refusing only stays compatible with "upgrades never break" because the list now covers every documented real-world setup, so only genuinely unknown keys hit it, and the operator can unblock those in one step without a release. The never-allow set keeps that escape hatch from re-opening what V13 closed.
- **Alternatives considered:** Revert to a denylist: refused, because V13 showed a denylist misses keys and a list of runnable variables can't be complete. Skip unknown keys with a notice (ADR-143): refused, because the agent then runs half-configured and possibly on a different model. Allow every `ANTHROPIC_*` and `CLAUDE_CODE_*` key by prefix: refused, because `CLAUDE_CODE_SHELL_PREFIX`, `CLAUDE_CODE_PROCESS_WRAPPER` and the plugin and config directories are exactly the code-execution vectors. Let the extra keys be set through MCP or by agents: refused, since that would let an agent widen its own allowlist. A per-provider allowlist: deferred, because one shared list is simpler and a key for another runtime is inert in a process that doesn't read it. Note that `OPENAI_BASE_URL` stays allowed but doesn't re-route Codex: the built-in provider takes its base URL from config, so re-pointing Codex needs a config override, not a preset.

## ADR-155: An agent's out-of-memory kill stays in that agent

- **Date:** 2026-10-24
- **Decided by:** The release engineer agent (ReleaseRollout), as an urgent bugfix TeamLead assigned with the goal and the options to weigh. Merges on the bugfix rule (nox + CI + a mutation-proven guard).
- **Context:** On a Linux install, an agent ran a large build and the kernel OOM-killed it. systemd's default `OOMPolicy=stop` then stopped the whole `autonomos` user unit, so the server and every agent died together. The generated unit had no OOM settings. Measured on systemd 255 / cgroup v2 with throwaway units:
  - (a) `OOMPolicy=stop` fails the unit with result `oom-kill`; `continue` keeps it running.
  - (b) Processes in a user unit start at `oom_score_adj` 200, inherited from the user manager. The kernel scores `rss + adj × (size of the OOM domain) / 1000`, so in a memory-capped domain the server, the bigger process, is the natural victim.
  - (c) systemd-oomd only kills *leaf* cgroups, or cgroups with `memory.oom.group` (systemd v255 `oomd-manager.c`). Today the unit itself is that leaf, so an oomd kill took everything whatever `OOMPolicy` said.
  - (d) A delegated user unit can move its processes into sub-cgroups, enable the memory controller for them, and read each sub-cgroup's `memory.events`.
  - (e) systemd's `memory.events` for the unit is hierarchical, so `OOMPolicy=stop` reacts to kills in sub-cgroups too. With `Delegate=` on, systemd defaults `OOMPolicy` to `continue` (`systemd.service(5)`), and the policy also governs the unit after a systemd-oomd kill.
  - (f) The cgroup carries no marker of delegation: no `user.delegate` xattr, and `cgroup.subtree_control` is writable either way.
- **Decision:** Layered, Linux only except the exit verdict:
  1. **Unit:** `OOMPolicy=continue` (explicit, not left to the `Delegate=` default, which `DefaultOOMPolicy=` and older systemd versions can change), plus `Delegate=yes` and `Environment=AUTONOMOS_CGROUP_DELEGATED=1` (by (f), the template has to say so). Existing installs get it through service-sync on their next update.
  2. **OOM score:** every agent's process tree (the PTY child, the Codex daemon, which is the server's child but runs the agent's commands, and their current descendants) is raised to `min(1000, base + 500)` right after spawn. The server keeps its base. An unprivileged process may raise its own-uid processes' scores, and a user unit can't lower its own, so this is the direction available. It applies with or without systemd.
  3. **Per-agent cgroups** when the marker is set: the server moves every process of the unit into a `server` leaf, enables `memory`+`pids` for children, and each agent gets `agent-<id>`. systemd-oomd then picks among the leaves, not the whole unit, and each agent's `memory.events` attributes its kills.
  4. **Telling the operator:** an agent whose main process is SIGKILLed from outside autonomOS gets a bell notice. It's "out of memory" when its cgroup counted an OOM kill, "most likely the OOM killer" when only the unit did, and otherwise systemd-oomd on Linux or memory pressure on macOS. The agent is resumed once in the same record, and a second kill within 10 minutes is reported and left down. A kill of a process an agent started, which the agent survived (a build), is reported for that agent.
  5. **No per-agent memory cap (`MemoryMax`) yet.** The mechanism is in place (an agent cgroup); a setting for it is follow-up work.
- **Rationale:** (1) alone stops the unit-wide stop but leaves the kernel free to pick the server (b), and it can't help against oomd (c). (2) makes the server the last choice in any kernel OOM and costs nothing. (3) is the only change that makes systemd-oomd's choice per-agent, and it also gives exact attribution. Each layer degrades on its own: no delegation still leaves (1)+(2), and non-Linux still gets the exit verdict. All of it is best-effort and never fails a spawn. Keeping agents *inside* the unit (sub-cgroups) rather than in separate transient scopes preserves the service's lifecycle: stopping the service still stops every agent, which restart and update rely on.
- **Alternatives considered:**
  - `OOMPolicy=continue` alone. It's what an operator would try first by hand, and it doesn't stop the kernel picking the server (measured) or oomd taking the whole unit.
  - Each agent in its own transient scope (`systemd-run --user --scope`). Scopes are siblings of the unit, not children, so stopping or restarting the service would leave agents running; ADR-105 measured that a transient unit survives a service restart. That breaks restart, update and the resume sweep.
  - `memory.oom.group=1` on agent cgroups. It would kill the whole agent, Claude included, when only its build needed to go; without it the kernel kills the biggest process, usually the build, and the agent carries on.
  - Marking the server's leaf `user.oomd_omit`. systemd-oomd honors that xattr on a user-owned cgroup (v255 `oomd-util.c`), but Node has no xattr API and `setfattr` isn't installed by default (measured). Left as a residual: oomd could still pick the server leaf if the server is the top consumer.
  - `OOMScoreAdjust=` in the unit to lower the server. A user unit can't go below its inherited score without privilege.
- **Source:** TeamLead's bugfix assignment on the agent channel (2026-10-24). Measured in a ReleaseRollout Claude Code session on forge (systemd 255, cgroup v2) with throwaway user units, never the live service. The CI guard `scripts/oom-isolation-ci.sh` runs the real rendered unit under real user systemd on every `check` run, and also proves that the pre-fix unit is stopped whole and that without the guard the server is the victim.

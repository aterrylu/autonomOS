## ADR-095: Sidebar drag-reorder revamp — whole-row NATIVE drag (dnd-kit built then rejected at the hands-on gate)

- **Date:** 2026-08-30 (dnd-kit build) → 2026-08-31 (pivot to native, shipped)
- **Who:** Terry (diagnosis + proposal reviewed, both scope options picked eyes-open, **hands-on gate rejected the dnd-kit grip**); implementation by the Shortcuts agent (milestoned, forked).
- **Context:** Terry: the agents-tab drag-reorder was "not accurate, not visual enough, doesn't feel like it did what I wanted." Deep-diagnosed (artifact 43d562db) — six failure modes, all rooted in **native HTML5 Drag-and-Drop's DEFAULT behavior**: the indicator drew on the hovered row's top edge while the commit was a plain splice, so downward drags landed one slot off (indicated≠committed, proven live); a 2px hairline with no lift; no freeze, so live polls shifted rows under the cursor mid-drag (proven — a fresh arrival moved the target +39px); no auto-scroll; hierarchy reorder-only with drop-ON≡drop-BETWEEN; and native DnD's un-styleable ghost / coarse hit-testing ceiling. **Key reframing from the pivot:** five of the six are fixable *within* native DnD by owning the hit-test, the freeze, the indicator, and a hand-rolled auto-scroll. Only the ceiling items (styled lift overlay, sub-pixel collision, keyboard reorder) genuinely require a library.
- **Decision (as shipped): whole-row NATIVE HTML5 drag, with the wins ported onto it.** dnd-kit was built first (milestones M1–M4) and **rejected by Terry at the hands-on gate**: "it looks terrible… I don't want that drag bar on the left, I want the whole agent to be draggable, not with the dedicated drag bar," and "in the hierarchical view, the lines used to line up like a tree but they don't anymore" (dnd-kit's per-item sortable wrappers broke the tree-guide alignment). So dnd-kit was removed and the improvements re-implemented on native:
  1. **The whole row is `draggable`** (no grip), on both views (flat pinned/unpinned + the hierarchy org-tree — Terry's default). The row body's native drag ALSO carries the pane (`DRAG_TYPE` in `dataTransfer`) so dragging into the terminal area still opens a tab/split — one gesture, disambiguated by drop target (sidebar row → reorder via the shared drag ref; dockview → tab/split).
  2. **Indicated == committed**, via ONE pure module per view (`sidebarReorder.ts`, `hierarchyReorder.ts`). `dropEdgeAt(clientY, rect)` picks the above/below half of the hovered row; `flatDropIndex(from, overIdx, edge)` / `hierDropIndex` derive the commit index from that SAME edge the slide-apart gap opens at (`insertionBoundary`) — so the indicator and the landing slot cannot diverge. Fully unit-tested (the accuracy bug, the no-op boundary cases, `insertionBoundary` == commit).
  3. **Slide-apart + ghost preview** (the indicator — replaced the gold insertion LINE at Terry's second hands-on gate). Terry re-tested the native build and rejected the line: "I did like the previous version where dragging them would push the other sessions away and preview the agent row in between the place to be inserted; I don't like the current version where it simply shows a yellow line." So the line was dropped for: the rows at/below the insertion boundary **push away** to open a one-row gap, a **ghost of the dragged row previews in the gap** ("preview the agent row in between"), and the drag **origin dims** in place. Mechanism (both views, one path): a real-height `DragGhostRow` is spliced into the render at the boundary slot, so ordinary layout flow pushes every following row — *and, in the tree, its whole subtree* — down by one row; the ghost's own height animates `0 → measured row height` on mount so that reflow is a smooth open, not a jump. This deliberately **avoids per-row transforms**, which in the non-contiguous tree would force wrapping each node *and* its subtree (siblings render separated by their subtrees) and detach the connector lines — the objection that had kept dnd-kit's slide-apart flat-only. The boundary is `insertionBoundary(overIdx, edge)`, the SAME slot `flatDropIndex`/`hierDropIndex` commit relative to, so the opened gap is exactly where the drop lands (indicated == committed, unit-tested). Row height is measured from the dragged row's rect at `dragstart` (rows vary — a meta line makes one taller). `onDragLeave` of the `<aside>` clears the gap, so dragging a row body toward the terminal (drag-into-dockview) never strands an open gap. The active/visible row highlight is untouched (the line's box-shadow composition is gone with the line). **Affordance continuity at the origin (Terry's third hands-on note — "when the drag hovers back over its original position there's no insertion indication… I think that might still be good to have"):** when the hover resolves to the dragged row's OWN slot no gap opens (a no-op), so the origin row *itself* takes the dashed-preview styling — a no-reflow `outline: 1px dashed` + the ghost's fill, at full opacity rather than the dimmed 0.4 — so there is always exactly one dashed "will land here" marker, including 'right back where it started.' This reuses the no-op the commit already computes: `flatDropIndex`/`hierDropIndex` return null **iff** the drop lands back at origin (`to === from`), so the geom exposes `originIsTarget = !committing` and origin-dash vs. in-gap ghost are mutually exclusive by construction (exactly one, never zero, never two). An `outline` (not a `border`) is used so it draws inside the box with no reflow and coexists with the 3px tree `borderLeft`. Still a no-op on commit — pure affordance.
  4. **Freeze at drag-start**, both views: the ordered rows (flat) / the whole tree (hierarchy) are snapshotted at `dragstart` and rendered from the snapshot until `dragend`, so live poll ticks can't shift the target mid-drag.
  5. **Hand-rolled edge auto-scroll** (`useDragAutoScroll` — a rAF velocity loop keyed off the cursor's distance to the scroll container's top/bottom), replacing dnd-kit's built-in.
  6. **Index-space fix (nox Thread-1), hierarchy.** The rendered tree is built `hideStopped=true`, so a group's rows are its LIVE siblings — but the persisted `hierarchyOrder[gk]` keeps STOPPED names too. Splicing a live-only index into the full persisted array moves the WRONG sibling whenever a parent has a stopped child. `reorderLiveInFullOrder(fullOrder, liveSibs, from, to)` reorders the live entries within the full order **by name**, leaving stopped names in their absolute slots (robust to a fresh live arrival missing from the persisted order). This replaced the old lazy-init + `reorderHierarchy(gk, from, to)` path that spliced tree-indices straight into the persisted array.
  7. **Re-parent DECLINED** (Terry, explicit). Hierarchy reorder is confined to a parent's direct children; a cross-parent drop is a no-op (the `onDragOver` guard only arms when `hierDrag.group === groupKey`). The **set-manager submenu (ADR-093) is the re-parent path.** Drop-ON stays indistinguishable from drop-BETWEEN by design. The tree-guide geometry (`TreeLineGuides`) is the native baseline's, so the tree lines line up again (Terry's second complaint).
  4. **Drop authority + commit-by-key (nox re-review hardening, after Terry's GO).** Three findings on the slide-apart build, all fixed before merge. (a) 🔴 **The opened gap was a drop dead-zone.** The ghost sets `pointerEvents:none`, so an upper-half hover leaves the cursor *inside* the ghost; drag hit-testing fell through to the plain container, which had no `onDragOver`/`onDrop`, so `dropEffect` was `none`, the browser fired no `drop`, and `dragend` cleared state without committing — releasing exactly where the gap invited silently cancelled the reorder. Neither test layer caught it because both dispatched `drop` directly on the target row, bypassing hit-testing (the faithful-oracle caveat this ADR records). Fix: the `<aside>` is now the **single drop authority** — `onDragOver` `preventDefault()`s whenever a drag is active (keeping the whole sidebar, ghost included, a live drop target) and `onDrop` commits from the already-correct `dropTarget`/`hierDropTarget` state; the per-row `onDrop` is gone (a row drop reaches the same handler by bubbling), so there is one commit path for both a row release and a gap release. Pinned by a dom test that drops on the container (not a row) and is mutation-verified RED without the handler. (b) 🟡 **Flat commit was index-based against the live list.** The freeze fixes the *view*, but `reorderFlat` re-derived sections from the live store at commit, where a mid-drag arrival prepends to unpinned — shifting every index and moving the wrong agent (the same index-space class as the hierarchy Thread-1 fix). Fix: `reorderFlat(section, dragKey, beforeKey)` commits BY KEY, resolving the frozen keys against the live list, so indicated == committed survives a poll tick. (c) 🟡 **Auto-scroll could run away on exit** and the `dragleave` used the unreliable `relatedTarget`. Fix: auto-scroll is fed from one source (the `<aside>` `onDragOver`, so it covers the ghost too) and stopped in a **geometry-checked** `dragleave` (compare the pointer against the box rect, not `relatedTarget`, which Chrome reports null for on drag events — the null path had collapsed-and-reopened the gap on every row crossing).
- **Losses accepted vs. dnd-kit (documented, not hidden):** the browser's default drag ghost still follows the cursor (alongside the in-gap preview), no sub-pixel pointer-sensor precision, and **no keyboard-Space reorder** (native DnD is pointer-only). The gap **moving** to a new boundary mid-drag is a one-row layout jump (only the first open animates); a smoothly-tracking gap would need per-row transforms + the tree-subtree wrapping this path deliberately avoids — a follow-up if Terry asks for it. Terry weighed these against "the whole agent is draggable + the tree lines are back" and chose native. If keyboard reorder becomes a requirement, it's a follow-up (arrow-key handlers on the focused row driving the same `reorderFlat`/`reorderLiveInFullOrder` commit — the pure modules already exist).
- **Rationale:** the pivot's core insight is that the six failure modes were native DnD's *defaults*, not native DnD itself — owning the four fixable ones (hit-test, freeze, indicator, auto-scroll) recovers the feel Terry wanted while keeping the whole row draggable and the tree guides intact, which the library could not. The commit reducers stay thin (`reorderFlat` unchanged; the hierarchy commit moved into the by-name `reorderLiveInFullOrder`), and the blast radius is the rendering layer + two small pure modules.
- **The load-bearing lesson (recorded for the team): drag correctness has a hierarchy of test oracles, and only the faithful ones count.** During the dnd-kit build a real-mouse activation bug — the grip sat inside the native-draggable body, so a real pointer started the browser's native drag before dnd-kit's 5px activation and dnd-kit never fired — passed *jsdom* tests, passed *synthetic-PointerEvent* browser probes, and even passed a *Playwright* spec a fork made green with synthetic events. Only a real OS mouse exposed it. The pivot's native e2e keeps the lesson: `e2e/sidebar-dnd.spec.ts` drives **native** `dragstart`/`dragover`/`drop` with a shared `DataTransfer` (CDP's `page.mouse` never raises native drag events, so it cannot exercise the `draggable` path at all), passing a `clientY` matched to the target's real rect so the above/below hit-test runs for real — and its accuracy assertion was RED-first verified (breaking `flatDropIndex`'s edge handling turns it red).
- **Alternatives considered:** **dnd-kit** (BUILT, then rejected at the hands-on gate — the grip was the dealbreaker Terry couldn't accept, and its sortable wrappers broke the tree-guide alignment; whole-row activation on dnd-kit reintroduces the native-drag-preempts-the-sensor conflict the grip existed to avoid, so "dnd-kit without the grip" was not a clean option); **patch only the accuracy bug in native, leave the rest** (rejected — the freeze and auto-scroll are what make it *feel* right, which was Terry's actual complaint); **hand-rolled pointer-events from scratch** (rejected — more surface than porting the four wins onto the existing native path); **drag-to-re-parent** (declined by Terry — the submenu owns re-parenting).

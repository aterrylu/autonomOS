## ADR-105: In-app update — release notes from GitHub, agent-aware pre-flight, out-of-band upgrader

*Numbering: drafted as ADR-101 and renumbered to the next free number from the tail as other PRs landed; re-checked at merge.*

- **Date:** 2026-09-24 — **Decided by:** Terry (asks + picks: busy default = wait for idle, idle window 30s, no skip-this-version, all releases since the user's version stacked newest-first; notes must be the GitHub release notes, one source); mechanics by the release engineer. Provisional number — renumber to next-free at merge.
- **Context:** The update badge (#323) only linked to GitHub; updating meant a shell. The old `POST /api/system/upgrade` swapped the bundle *inside the daemon* and exited — the in-band pattern ADR-077 warned about (the process cannot be the agent of its own restart, and it runs no health gate), bundle-only, and never wired to a button.
- **Decision:**
  1. **One source for notes.** The server's cached update check (ADR-077 §6) also fetches every published, non-draft, non-prerelease release in (current, latest] from the GitHub releases API and caches each **body verbatim** — the themed notes `/release` publishes. `GET /api/system/releases` serves them; the dashboard renders them newest-first with a dependency-free markdown→React renderer that never injects HTML (raw HTML renders as text; only http(s) links become links). No bundled notes file, no second changelog. A notes fetch failure caches `null` → "notes unavailable — view on GitHub"; notes never gate the update. The dashboard still never contacts GitHub.
  2. **Out-of-band upgrader, in its own supervisor scope.** `POST /api/system/upgrade` launches `autonomos upgrade --status-file` — the existing spine with health gate + auto-rollback — as a separate job: a `systemd-run --user` transient unit, or a one-shot launchd job labelled `<daemon label>.upgrade`. **Measured before building:** under systemd a `setsid`/`nohup` child of the service is **killed** by `systemctl --user restart` (our unit sets no KillMode → default control-group kill); a transient unit **survives**. Under launchd both a setsid child and a separate job survived `kickstart -k`; the separate job is used on both platforms for one uniform guarantee. `systemd-run` expands `$` in arguments (observed), so arguments are escaped. The old in-process swap-and-exit path is removed. A daemon not under a supervisor (detected from the supervisor's own env: `INVOCATION_ID` / `XPC_SERVICE_NAME`, both verified) refuses: nothing could restart it — the UI says to run `autonomos upgrade` in a terminal.
  3. **Progress never flows through the daemon being restarted.** The job writes `$configDir/upgrade-status.json` (atomic temp+rename) phase by phase (downloading/verifying/installing or fetching/building, restarting, done | rolled_back | failed with a reason). While up, the daemon serves it (`GET /api/system/upgrade`); across the gap the dashboard polls `/api/system/version` with its existing cookie until the target answers, reads the final record, and hard-reloads. A 401 after reconnect is shown as an explicit error, never a silent login screen (auth-continuity invariant, ADR-089).
  4. **Agent-aware pre-flight, one predicate.** Busy = `working | tool_running | needs_input | compacting | orchestrating` on a running agent; the same `listBusyAgents()` feeds the dashboard's pre-flight list and the scheduler. The UI states plainly per agent what a restart costs (PTYs close and resume via ADR-049; a mid-turn agent stops and does not continue on its own; a running command is killed — Codex keeps its thread, ADR-100; a pending question is dismissed). Default = **wait for idle**: armed with a target, launch only after **30s of continuous idle**; any new turn resets the window. Armed state is in-memory — a daemon restart for another reason disarms it (the safe direction). "Update now" names exactly what it interrupts.
  5. **Operator-only trigger.** Not an MCP tool; not mounted on the internal control socket; the route requires the dashboard's login cookie and refuses `X-Agent-Token` and bearer-only calls (tests pin all three). **Honest boundary:** an agent's MCP config carries the operator token, so an agent deliberately forging a browser request could pass — the same trusted-fleet boundary as every operator route (ADR-067's caveat). The guard closes every agent-*facing* path, not a determined forgery.
  6. **Source installs:** `make build` builds the dashboard into `dist.next` and swaps, so the old daemon — still serving throughout the minutes-long rebuild — never serves an emptied `dist/`.
  7. **Amendment — state snapshots, verification, and code+state recovery (Terry's picks, same day).** The health gate protects the *daemon*; it does not protect agent *state* — a rollback that restores code but not records runs old code on records a newer version may have rewritten, and nothing snapshotted state (the Codex crash incident needed a hand-made backup tarball to recover thread mappings). Measured: the state an update can break is small and local (forge: < 200 KB — agent records, agent tokens, schedules, templates, presets, hand-off queues, settings, token); conversations live outside `$configDir` and an update never touches them — what breaks is autonomOS's *mapping* to them. So:
     - **Snapshot before every update** (dashboard or shell): `autonomos upgrade` copies those entries into `$configDir/snapshots/<from-version>-<stamp>/` (staged + renamed, modes preserved — secrets stay 0600, dir 0700; logs/sockets/pid/run history excluded) with a manifest carrying the per-agent id/thread baseline. **Fail-safe: no snapshot, no update.** A run that changes nothing (up to date, or failed before the install step) deletes its snapshot, and pruning happens only after something changed — pruning at creation would evict a real snapshot per no-op attempt. Retention: last 5. `autonomos snapshots list` shows them with paths.
     - **Verify after every update:** the new daemon waits for the job's `done`, lets resumes settle, and compares live agents with the snapshot baseline — record present and loaded, provider session/thread ids byte-identical, running-before is running-again. The verdict goes into the status record; the success banner says "all N verified" or names each agent that needs attention next to **Restore previous version**. It warns; it never restores behind the operator's back. It is not an end-to-end turn probe, and says only what it checks.
     - **Code and state move together:** every path that puts an older version back — the health gate's auto-rollback, `autonomos rollback`, the in-app Restore (`POST /api/system/rollback`, operator-only, same out-of-band job) — stops the daemon, restores the code, restores the snapshot taken FROM that version, then restarts. With no pairing snapshot (installs from before snapshots) the rollback is code-only and says so. A restore destroys nothing and never leaves state half-done: the live state is first saved as its own snapshot (so what the newer version wrote — agents, schedules, preset keys — survives, and rolling forward again pairs with it); entries are staged, then swapped in by rename with undo on failure; and it refuses outright if the daemon didn't confirm stopped. In-app, only the snapshot that pairs with the kept previous version is one-click restorable; older ones are listed for reference/manual recovery.
  8. **STANDING RULE — no irreversible migrations.** A change to the agent-record format (`AGENT_SCHEMA_VERSION` bump) must: (a) keep the pre-update snapshot sufficient to go back (restore pair), (b) be refused LOUDLY by older code — the loader now skips any record with a higher `schemaVersion` with an error naming `autonomos rollback`, never loading (so never re-saving) it in the old shape, and (c) be announced BEFORE the click: the release body carries the structured marker `<!-- autonomos:storage-format-change -->` (invisible on GitHub; the `/release` skill adds it), which the server parses into `storageFormatChange` and the dashboard shows as a pre-click callout. Never inferred from prose.
- **Rationale:** The daemon cannot be the agent of its own restart — measured: a detached child of the service dies with it under systemd's cgroup kill, while a separate supervisor job (`systemd-run --user` / one-shot launchd job) survives — so the updater runs out of band and reports through a status file, never through the process being restarted. The health gate protects the daemon but not agent state, so every update snapshots state first and every way back (health-gate rollback, `autonomos rollback`, Restore) restores code and state as one pair; restoring is always the operator's click, never automatic. "Wait for idle" is the default because interrupting an agent mid-turn costs work, and idle is re-checked right before the irreversible step because idle at launch isn't idle minutes later. Notes come from the GitHub release bodies because a second copy would drift. Only the dashboard operator can trigger it because agents must not update or restore the host they run on.
- **Alternatives considered:** a detached child of the daemon (rejected: measured killed by systemd's cgroup kill); keeping the in-process swap (rejected: in-band, bundle-only, no health gate); a bundled/hand-written notes copy (rejected by Terry: one source); a client-side markdown library (rejected: new dependency + sanitizer surface; our notes use a tiny subset); persisting the armed state across restarts (rejected: a surprise update after an unrelated crash is worse than re-arming).
- **Source:** Terry's asks/picks via TeamLead (2026-09-24), design artifact (10 screens), supervisor measurements on forge (systemd) and macOS (launchd) with test labels only.

## ADR-100: Codex crash-net retains the resumable thread — the destructive force-fresh arms only behind a pre-flight

- **Date:** 2026-09-17 · **Decided by:** Terry (production bug report + "address it before any new releases"), root-cause + fix by CodexGemini@autonomOS, GO on Option A relayed via TeamLead.
- **Context:** In production, multiple Codex agents crashed (`codex` process `exitCode=1`) after short uptimes, and their conversation threads became unrecoverable — recovery required restoring a backup. Each had a known `providerThreadId`, so `codex resume <threadId>` could have revived it. The report read as "crashed, gone." This extends the ADR-049 crash-net (which kept Claude Code agents resumable across a crash rather than vanishing) to the Codex/`providerThreadId` path, where the *opposite* was happening.
- **Root cause (retain-vs-purge asymmetry, confirmed in code):** the ADR-049 onExit safety net (`runtime.ts`, `resumeSafetyNetArmed` + the force-fresh block) fires on `attemptedResume && lifetime<5s && exitCode!==0` and force-freshes: reset `providerSessionId`, **clear `providerThreadId`**, respawn fresh. Arming was `!!providerThreadId || (resumeSessionId && hasResumeHook)`. The asymmetry is NOT a hard-delete (`markExited` always retains the record, and there is no hard-delete anywhere in the crash flow) — it is the destructive **force-fresh**:
  - **Claude Code** arms only via `resumeSessionId && hasResumeHook`. The `hasResumableSession` pre-flight runs before spawn and *clears* `resumeSessionId` when nothing is resumable on disk — so by the time CC can arm, a session **provably existed but resume still crashed** (likely corrupt); force-fresh loses little (ADR-049's never-conversed/corrupt case).
  - **Codex** has **no pre-flight hook**, so the net armed purely on a bare `providerThreadId` — *blind*, with zero evidence the thread was the cause. A `codex` process exits 1 for many reasons unrelated to the thread (environmental / upstream — the "Layer 1" cause, treated as opportunistic and NOT blocking). When it did, the net cleared a perfectly resumable thread and respawned fresh.
  - **Why a backup was needed (reconciliation, verified on disk):** the Codex rollout persists *by thread* (`~/.codex/sessions/.../rollout-<ISO>-<threadId>.jsonl`, thread id in the filename + the `session_meta` line with `cwd` + `originator`), and autonomOS never deletes rollout files — so the conversation was **intact on disk**. But `providerThreadId` lives ONLY on the Agent record; clearing it **severs the sole agent→rollout link**. With multiple crashed agents sharing a cwd the orphaned rollouts can't be reliably re-attributed → practically unrecoverable without the backup that preserved the associations.
- **Decision (Option A):** the destructive force-fresh net arms **ONLY behind a pre-flight that proves the resume target is the culprit** — `resumeSafetyNetArmed` drops the bare-`providerThreadId` term and returns `!!resumeSessionId && hasResumeHook`. A Codex resume-crash (no pre-flight) therefore **falls through to the normal exit path → `markExited("crashed")` with `providerThreadId` INTACT** = retained crash-but-resumable, revivable via `codex resume <threadId>` (the primitive proven live in the Projects-discovery investigation). No respawn loop: retain is terminal (an exited/crashed record is not auto-resumed on boot). CC behavior is unchanged. The invariant is provider-agnostic — "no destructive force-fresh without a pre-flight" — so any future thread-based provider is safe-by-default until it earns a pre-flight.
- **Rationale:** the ADR-049 remedy was sound *given its precondition* (proof the session is at fault); Codex was handed the remedy without the diagnosis. Retaining beats auto-recovering when the failure is silent and the asset is irreplaceable: a crashed-but-resumable row the user resumes by hand is strictly better than a silent thread purge — visible, bounded, reversible, and never data loss. A genuinely-corrupt thread now shows crashed and a manual resume re-crashes (visible, no loop), instead of auto-freshing away a good conversation on every environmental crash.
- **Future work:** safe auto-recovery for Codex (Option B) — a rollout-read pre-flight analog to `hasResumableSession` that confirms the thread exists/looks resumable, so the net force-freshes only a *provably-bad* thread (the `codexRollout.ts` reader from the F3/unread work already provides the primitive). And a best-effort **repair** for records already damaged pre-fix: re-associate orphaned `originator=autonomos-gateway` rollouts by cwd (best-effort — ambiguous with shared cwds). Neither is release-gating.
- **Alternatives considered:** **Option B (Codex pre-flight) now** — rejected as the gating fix (bigger surface + its own tests; deferred to future work). **Keep force-fresh but stash the old `providerThreadId` in a recovery field** — more state + UI for a case Option A already prevents. **Do nothing / rely on backups** — rejected (the harm is silent conversation loss). **A live-PTY test of the onExit path** — rejected for CI (ADR-049 documented that live-PTY assertions are flaky under CI/root); the fix is pinned at the pure-function boundary (`resumeSafetyNetArmed`) plus a store-level retain test (`markExited` keeps the thread), which together cover the full chain without a PTY.
- **Source:** Terry production report relayed via TeamLead 2026-09-17 (sanitized — no confidential agent names/session/thread ids; all repro/tests use synthetic ids). Root-cause report + design fork + GO on Option A over the autonomOS agent channel.

## ADR-123: Release tags must be on main: consumers verify ancestry, release.yml gate, tag ruleset

- **Date:** 2026-09-30
- **Decided by:** Terry approved fixing the security audit findings ("yes for all the security items"); SecurityFix-Hardening (agent) chose the shape, TeamLead approved the repository ruleset before it was applied, and SecurityAudit-Claude reviewed.
- **Context:** Security audit V5 (High): a `v*` tag push skipped main's review and shipped everywhere. The only ruleset protected the `main` branch, and nothing protected tags. `release.yml` built and published any `v*` tag as `latest`. The source-mode updater (`sourceUpgrade.ts`) and `install-source.sh` checked out the highest semver tag and ran its `make build`, so the tagged commit's code executed on every source install. The audit's PoC upgraded a fixture from 1.0.0 to 9.9.9 on an off-main tag, and that commit's Makefile ran. Four accounts have push access.
- **Decision:**
  1. **Source-mode consumers verify ancestry on the user's machine.** `latestVersionTag` lists only tags `--merged refs/remotes/origin/main`. An explicit version pin must pass `git merge-base --is-ancestor`. Both fail closed when `origin/main` is missing. `install-source.sh` does the same in a sourceable `pick_release_tag`.
  2. **`release.yml` gains a read-only `on-main` job** that the publishing job needs. It never installs or runs the tagged commit's code. It applies to tag pushes and to `dry_run=false` dispatches; dry-run builds from any branch stay possible.
  3. **A tag ruleset on `refs/tags/v*`** restricts creation, update and deletion to the repository-admin role. `version.yml` pushes release tags with the owner's `RELEASE_PAT`, so releases keep working.
- **Rationale:** The three layers do different jobs, and the ADR says which is which so none is over-trusted. For a tag push, GitHub runs `release.yml` from the tagged commit itself, so a deliberate off-main tag can delete the workflow gate from its own copy; that gate catches only accidents (a tag cut from the wrong ref, a publishing dispatch from a feature branch). The ruleset is what stops a non-admin writer from creating the tag at all. The consumer checks hold even if both fail, because they compare against `origin/main`, which is protected by the merge ruleset and checked on the installing machine.
- **Alternatives considered:** (a) Only the workflow gate (the audit's S sketch). Rejected as a boundary: the workflow file comes from the attacker's commit. Kept as the accident catcher. (b) Only the ruleset. Rejected: a single repo setting, silently removable, with nothing downstream noticing. (c) Signed tags verified by consumers. Rejected for now: key distribution plus the `version.yml` bot identity make it a larger change, and ancestry gives the same "went through review" property for source installs. (d) Also verify ancestry in bundle mode (`install.sh`, `upgrade.ts`) through the GitHub API. Rejected as insufficient: a release's tarballs aren't bound to its tag's commit without attestation verification. **Not covered here, and stated as open:** a writer can still create a GitHub Release by API or dispatch without a tag push, and bundle-mode installs trust `latest` plus the same-release `SHA256SUMS`. Closing that needs consumers to verify the published SLSA provenance, including that its source commit is on main (the audit's longer-term M). It is proposed as a follow-up.
- **Source:** Security audit phase 1 report (SecurityAudit-Claude, finding V5); PR for `terry/release-tag-ancestry`; TeamLead approval of the ruleset call over the agent channel.

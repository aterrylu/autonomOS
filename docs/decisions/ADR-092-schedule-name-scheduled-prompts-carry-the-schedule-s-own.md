## ADR-092: schedule://<name> — scheduled prompts carry the schedule's own sender identity

- **Date:** 2026-08-27
- **Who:** Terry (picked from three proposals by the APIConsolidation agent); implementation by the agent
- **Context:** A scheduled prompt arrived attributed to `agent://Scheduler` — an address that looks replyable and names an agent that has never existed. BASE_CONTEXT teaches "reply via from_uri", so agents dutifully tried, failed resolution, and went hunting through list_agents (reproduced live in the v0.6.0 forge smoke). PR #330 shipped the stopgap: a name-keyed courtesy message after resolution fails. The structural questions remained: what namespace do system senders live in, and does a real agent named "Scheduler" collide? Three options were proposed (one `system://` scheme for all system senders; per-category `schedule://<name>`; hybrid `system://schedule/<name>`). Terry chose `schedule://<name>` — per-schedule identity as its own scheme.
- **Decision:**
  1. The scheduler sends with sender id `schedule:<name>` (mirroring the `agent:<name>` convention its TARGETS already use). The router's `resolveSenderIdentity` renders it as display name `Schedule <name>` with `from_uri schedule://<name>` — stamped identically on both delivery paths (channel-server payload for Claude Code, `formatInbound` for Codex), so the terminal header reads `[Schedule <name> → you via schedule://<name>]` and the receiving agent knows WHICH schedule fired (several schedules can target one agent).
  2. `routeMessage` gains a `schedule` scheme branch that answers a reply attempt ACTIONABLY — schedules cannot receive replies; the message says so and names `get_schedule("<name>")` / `update_schedule` / `delete_schedule` with the name pre-filled — never "Unknown URI scheme", and never a pointer at list_agents.
  3. BASE_CONTEXT (MCP_INSTRUCTIONS) teaches the scheme in one line under "Receiving messages". Reaches new spawns only; live agents learn from the router's reply, which is the teaching moment by design (the broadcast:// removal precedent, ADR-064).
  4. **Name reservation is unnecessary** (the #330 reviewer's concern): a real agent named "Scheduler" — or one sharing a schedule's name — lives at `agent://<name>`, a different namespace from `schedule://<name>`. Collision is impossible at the URI level, so nothing is reserved at agent-create time.
  5. **Compat:** `SYSTEM_SENDER_NAMES["scheduler"]` and #330's `agent://Scheduler` courtesy reply are kept for one release — agents spawned before this change hold transcripts whose from_uris say `agent://Scheduler`, and anything still passing the literal `"scheduler"` sender id renders sanely. Both go with the next-release alias cleanup (ADR-084's).
- **Rationale:** Terry weighed one-scheme-for-all-system-senders (and the hybrid path variant) against scheme-visible schedule identity and chose the dedicated scheme. A future system sender category (watchdog, platform notice) adds its own scheme or a `system://` umbrella then — deliberately deferred rather than pre-built.
- **Alternatives considered:** `system://scheduler` (one rule for agents, but the header loses which schedule fired); `system://schedule/<name>` (one scheme + structured path; recommended by the proposing agent, not chosen); query-param identity (`?schedule=` — our URI handling is scheme://path, no query layer).
- **Source:** Terry via TeamLead relay 2026-08-27 ("let's go 2. schedule://<name>"), proposals in the APIConsolidation session.

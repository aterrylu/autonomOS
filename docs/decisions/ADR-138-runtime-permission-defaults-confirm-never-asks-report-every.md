## ADR-138: Runtime permission defaults: confirm never-asks, report every change, the UI in native values

- **Date:** 2026-09-30
- **Decided by:** Terry (the scope and the design mockup, relayed by TeamLead); an agent (CodexGemini) proposed the reframing of (a), which TeamLead approved
- **Context:** ADR-115/119 moved permissions to each CLI's own values and made the operator's per-runtime default a server setting (`runtimeDefaults`). That default is what every spawn uses when nobody names a permission, including every agent another agent starts. So a default changed to a value that never asks (`bypassPermissions`, `approval_policy=never`, `yolo`) silently widens the whole fleet. The dashboard still showed the old shared vocabulary (Ask / Accept edits / Plan / Bypass) and kept a browser-only "Permission Mode" preference that seeded Create Agent in one browser and nothing else. The template editor also rebuilt its save payload from its own fields, which dropped a template's canonical `permissions` pins on every save.

  The first proposal was "make the defaults operator-only at the route". The review found that isn't achievable today. Agents run as the same OS user as the server. Every Claude Code agent's argv carries the server token (`--mcp-config`, finding V3, owned by the security track). And `settings.json` is writable by that same user. A route check therefore restricts nothing that an agent can't do by editing the file or replaying the token.
- **Decision:**
  1. **Confirm on the server.** A `PUT /api/settings` that changes a runtime's default FROM a value that asks TO one that never asks is refused (400, `code: CONFIRM_NEVER_ASKS`, naming the runtimes) unless the body carries `confirmNeverAsks: true`. Re-saving a default that already never asks, or narrowing it, needs no confirm.
  2. **Report every change, however it happened.** `runtimeDefaultsWatch.ts` compares the effective defaults with the last-seen set (persisted in `$configDir/runtime-defaults-seen.json`, 0600). The first sight is the silent baseline. Each change pushes a notification to the bell, sent by "autonomOS" (`SERVER_NOTICE_KEY`); it says "never ask" when the new value doesn't ask. Each change also logs a warning and appends to a capped (20) change log that Settings shows. The check runs on every settings read and write, at boot, and on every spawn that falls back to the default. So an out-of-band edit of `settings.json` is reported, marked "outside autonomOS", before any agent runs on it.
  3. **No MCP path writes the defaults.** No MCP tool is a settings writer, and no tool schema carries `runtimeDefaults` or `confirmNeverAsks`. A test pins both.
  4. **The dashboard speaks each CLI's values** (the approved mockup):
     - **Settings → Runtimes** lists each installed CLI with its drift-probe line. Its default is edited per axis. A never-asks value is amber (the Needs-input color) and asks for an inline confirm before it's sent. Recent changes are listed.
     - **Create Agent** shows the runtime's values as cards, marks the operator default, and shows "Will run as" plus where the value comes from (picked here, template pin, or your default). Only a value picked in the form is sent; an untouched form lets the server resolve template pin → default.
     - **Templates** show a per-runtime pin, "overrides your default X", or "follows your default". "Use default" drops a pin, but when the default is wider than the pin on any axis (`widerAxes`, using core's `PERMISSIVENESS` order) it names exactly what widens and asks first. Saves keep the pins and every field the editor doesn't show. A legacy `permissionMode` saves as the explicit per-runtime pins it always ran.
     - **The Org Chart inspector** shows the canonical value, amber with "never asks" when it doesn't ask.
     - Codex's Plan is a hint (toggle it inside Codex with Shift+Tab), never an option.
  5. **The browser-only Permission Mode preference is removed.** A stored value is ignored and dropped on the next write. It is deliberately NOT migrated into the server default: moving a browser's `bypass` into the default would be exactly the silent widening this ADR forbids.
- **Rationale:** With agents and the server sharing an OS user and a leaked token, the achievable guarantee is that no widening is silent, not that it's impossible. A server-side confirm catches the honest mistake on every client, not only this dashboard. Reporting every change, including direct file edits, turns the unpreventable case into a visible one, at the place the operator already watches (the bell). Showing the CLI's own values removes the translation that made "Bypass" on Codex mean something different from "Bypass" on Claude.
- **Alternatives considered:**
  - *Operator-only route (reject non-dashboard writers):* no reliable way to tell the operator from an agent holding the same token, and the file stays writable. It would read as protection it doesn't give.
  - *Confirm only in the dashboard:* any other client (curl, a script, an agent) would skip it. The server is the one place every writer passes.
  - *Refuse never-ask defaults entirely:* removes a legitimate operator choice. Per-agent `bypass` is already allowed.
  - *Migrate the browser preference into the server default:* silently widens every agent-spawned agent for anyone who had picked Bypass locally.
  - *An argv preview in Create Agent* (in the mockup): left out because it would duplicate each provider's argv builder in the dashboard, a second source that can drift. The canonical value plus its caveats is what the spawn passes.
- **Residuals, stated plainly:**
  - **(c) Agent-initiated spawns with an explicit permission.** An agent may still name any canonical value in `create_agent` (e.g. `approval_policy=never`), and that value wins over every default. This is the trusted-fleet assumption of ADR-067. It is visible (the inspector shows it amber) but not prevented. Optional follow-up: *a child can't be more permissive than its spawner*, i.e. clamp a requested permission to the spawning agent's own via `widerAxes`, unless the operator starts it.
  - **The defaults boundary is detection, not access control, until V3 lands AND agents run as a separate OS user.** Only then can the server tell an operator write from an agent write, and only then can `settings.json` be out of an agent's reach. Until both, this ADR's guarantee is "never silent".

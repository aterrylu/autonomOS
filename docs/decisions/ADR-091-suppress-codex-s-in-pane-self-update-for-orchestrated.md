## ADR-091: Suppress codex's in-pane self-update for orchestrated sessions

- **Date:** 2026-08-27
- **Who:** Provider agent (T1 bug fix), under TeamLead@autonomOS relaying Terry's report + ack.
- **Context:** Terry: starting a codex session sometimes shows an update notification, and accepting it "breaks the session, session gets killed." Root cause: codex is a standalone install (`~/.codex/packages/standalone/releases/<ver>/bin/codex`) that shows an update popup at TUI startup (`codex-rs/tui/src/update_prompt.rs`); accepting it runs the self-updater, which swaps the binary in place and restarts the process — which our node-pty session sees as a process EXIT, so the session is marked killed.
- **Decision:** Every interactive codex TUI spawn passes `-c check_for_update_on_startup=false` (a shared `SUPPRESS_UPDATE_PROMPT_ARGS` pushed onto BOTH `buildArgs` paths: the sidecar `--remote` / `resume --remote` path and the legacy in-process path). This gates the popup off — the check is `config.check_for_update_on_startup` in `codex-rs/tui/src/updates.rs`, where `get_upgrade_version_for_popup` returns `None`, so no popup renders and the self-update can't be triggered. Kept OFF `daemonConfigArgs`/`buildSidecar` (the `app-server` daemon has no TUI and no popup). Pinned by a test asserting the flag rides all three interactive paths, so a future `buildArgs` refactor can't silently drop it on one.
- **Rationale:** autonomOS manages the codex binary version, so an in-pane self-update is never appropriate for an orchestrated session. Suppressing the trigger is simpler and safer than the alternative — detecting an update-restart vs a real process exit and re-spawning — a heuristic that would misclassify genuine exits. The value form is load-bearing: the bare boolean `check_for_update_on_startup=false` parses as a bool, whereas a quoted `"false"` is rejected by codex's config parser (`invalid type: string, expected a boolean`) — empirically confirmed on an isolated `CODEX_HOME`.
- **Alternatives considered:** handle the update-restart gracefully (rejected: a restart-vs-real-exit heuristic is fragile and misclassifies real exits); a one-time user edit to `~/.codex/config.toml` (rejected: fixes only one machine, and mutating the user's config is an ownership problem the `-c` override sidesteps). A deliberate `codex update` run as a standalone command is out of scope and unaffected.
- **Residual risk (documented, bounded):** codex silently accepts unknown `-c` keys (no warning; `--strict-config` does not cover overrides), so a future codex that renames or removes `check_for_update_on_startup` turns this flag into an *undetected* no-op — the popup returns and the session-kill regresses, indistinguishable from a normal exit. The test only asserts we emit the flag, not that codex honors it (CI has no codex binary). Bounded because Terry pins the codex version, and each version bump is the checkpoint (re-confirm via `codex -c check_for_update_on_startup=false doctor --all` → "startup update check" = false). **Follow-up (not built):** a doctor-style runtime probe that asserts the setting under the flag and logs a `SystemWarning` if the key stops being honored would make this self-detecting.

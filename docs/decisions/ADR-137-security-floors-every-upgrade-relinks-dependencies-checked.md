## ADR-137: Security floors: every upgrade relinks dependencies, checked in CI, at boot and in status

- **Date:** 2026-10-01
- **Decided by:** TeamLead@autonomOS (approved the proposal), implemented by SecurityFix-Hardening@autonomOS (agent)
- **Context:** Security audit V12b: `ws` before 8.21.1 keeps every fragment of an unfinished message, so a connected peer can grow the server's memory until it crashes (8.21.0 added a limit but didn't count empty fragments). Bumping `ws` in packages/server/package.json was not enough, for two measured reasons. (1) bun keeps a per-parent nested copy whenever the parent's range allows it: after the bump, `@hono/node-ws`, which builds every WebSocketServer the server accepts connections on, still loaded ws 8.19.0. (2) `bun install` on an existing tree doesn't relink a nested copy the new lockfile no longer lists. A faithful replay (a clone installed at main, then checked out at the fix and built with `make build`) still served ws 8.19.0. Every upgrade path runs `make build`: the in-app update and `autonomos upgrade`/`rollback` (sourceUpgrade.ts), install-source.sh (`make prod`), and a dev `git pull && make prod`. So every source install would have "upgraded" and stayed vulnerable. V12's hono bump had left the same kind of nested copy.
- **Decision:** (1) `make build` keeps its plain `bun install`, then runs `scripts/check-security-floors.ts`. That checks the installed tree and, ONLY when a floor is unmet or unverified, relinks once with `bun install --force --frozen-lockfile` (bounded at 10 minutes) and checks again. If the floor is still unmet, the build fails with the fix. `--force` relinks the nested copies a plain install keeps. `--frozen-lockfile` stops it from re-resolving: bun documents `--force` as "always request the latest versions", and a source install runs the operator's own bun. The relink is conditional because `--force` contacts the registry even with a warm cache. Measured offline: a plain frozen install of a healthy tree takes 0.3 s, while `--force` was still retrying after 5 minutes. A relink that fails (killed mid-retry, offline, cold cache) left the existing tree intact and runnable (measured), so the build fails without breaking the running install. (2) `SECURITY_FLOORS` in packages/server/src/securityFloors.ts is the one table of security minimums (ws ≥ 8.21.1, hono ≥ 4.13.12), each with the packages that load it at runtime. Adding a floor is one line. (3) A CI guard (security-floors.test.ts) requires bun.lock to pin each floored package exactly once, at or above its floor. A second nested entry is refused even when it's above the floor, because that's the shape that hid both stale copies. (4) The same table drives a check of the installed tree, resolving each package the way Node does from each consumer's real path. A consumer or package that doesn't resolve is reported as "unverified", never skipped, because skipping turned "couldn't look" into a pass for exactly the nested copy this targets. `seenBy` is maintained by hand; the bun.lock one-copy guard is the backstop for a consumer it doesn't list. The check logs a loud SECURITY warning on every boot and gives `autonomos status` a "security floors: ok / NOT MET / n/a (bundle install)" line. It never blocks startup and never changes `status`'s exit codes, which are a contract for scripts. It returns nothing for a bundle install, whose dependencies were inlined at release-build time from a fresh install. (5) ws-fragment-flood.test.ts builds a server exactly as production does (`createNodeWebSocket`, which takes no options, so ws's defaults are the only limits) and requires a 20,000-empty-fragment message to be closed with 1008, while a 1 MiB paste and a 2,000-keystroke burst still arrive.
- **Rationale:** A security fix only counts when the code that RUNS has it. The lockfile guard stops the repo from shipping a nested vulnerable copy. The build-time repair makes every upgrade apply what the lockfile says, without making a healthy offline build depend on the network. The boot/status check covers trees nothing else reaches: a dev checkout that skipped `make build`, an install upgraded before this change, a hand-run `bun install`. The fragment-flood guard tests the actual WebSocketServer construction, so it fails whatever the reason the wrong ws gets loaded. That's how the nested copy was found in the first place.
- **Alternatives considered:** An unconditional `bun install --force` in `make build` (the first version of this PR): it relinks every time, but hangs every offline build because `--force` always contacts the registry. A bun `overrides` block: declares a floor, but by itself doesn't relink an existing tree's stale nested copy. `rm -rf node_modules` in the upgrade: also relinks, but it's slower and needs the network when the cache is cold, and `--force` measured the same result. Exposing the check on the unauthenticated `/api/host` (which `autonomos status` already reads): refused, because it would tell anyone who can reach the port which vulnerable dependency the server runs. The CLI runs the same check locally against the same tree instead. A dashboard banner: deferred, because the per-session notification store has no server-wide channel, and SecurityFix-Auth's open #475 is reworking the one boot warning already plumbed toward the dashboard (V2b's `tokenWarning` field on `/api/system/version`); a shared boot-warning surface belongs with that work. Failing the boot on a violation: refused, because the fix is one command and a server that won't start strands every agent. Migrating to @hono/node-server 2.x's native WebSockets: deferred as non-security hygiene. Its advisories don't reach us (GHSA-9mqv affects only 2.0.0–2.0.9; GHSA-rmxm's serveStatic double-decode has no middleware to bypass on our static paths and was independently probed by SecurityAudit-Claude), and `@hono/node-ws` 1.3.x peers node-server ^1.19.
- **Source:** autonomOS security audit P1 (V12/V12b); agent channel with TeamLead@autonomOS, 2026-10-01 (proposal and GO on 1+2+3); review suggestion from SecurityAudit-Claude@autonomOS on #477, and its review of #482 (frozen lockfile, unverified instead of skipped, explicit n/a).

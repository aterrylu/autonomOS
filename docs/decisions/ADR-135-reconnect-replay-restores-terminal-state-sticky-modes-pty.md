## ADR-135: Reconnect replay restores terminal state: sticky modes, PTY geometry, repaint nudge

- **Date:** 2026-10-01
- **Decided by:** Terry (via TeamLead: "GO with 2 + 3", then, after Terry's live check, "redesign so a reconnected pane behaves exactly like a fresh healthy pane"; GO on spawning Codex inline); implemented by TerminalRender (agent)
- **Context:** Terry hit two terminal bugs on main. (A) Individual Codex panes "froze": the wheel did not scroll the transcript. (B) A Claude Code pane with `CLAUDE_CODE_NO_FLICKER=1` went black except the regions that repainted. Both were reproduced on an isolated rig with real agents. **(A), the real cause:** Codex changed its default to the ALTERNATE SCREEN (0.159.3, measured: `?1049h` + `?1007h` at startup; with `tui.alternate_screen="never"` it emits neither). xterm.js has no scrollback on the alternate screen and ALWAYS turns the wheel into ↑/↓ arrow keys there (it ignores `?1007`: `CoreBrowserTerminal.ts`, "convert wheel events into up/down events when the buffer does not have scrollback"). In Codex, ↑ walks the PROMPT HISTORY. So the transcript could not be scrolled at all, and a reconnect replay merely decided which broken state a pane landed in: a trimmed replay that lost `?1049h` put the pane on a normal screen with no scrollback (wheel inert: "frozen"), while an intact one kept it on the alternate screen (wheel → prompt history). A first fix that restored `?1049h` turned the freeze into the history walk; Terry rejected it live ("it's literally rolling over past messages in the text box"). Ground truth was then measured in a REAL headless Chromium (an occluded automation window freezes requestAnimationFrame, which xterm 6's wheel scrolling runs on, so earlier wheel observations there were invalid). **(B):** every terminal socket open resets the pane's xterm, and the server replays its output buffer: the last 1MB of raw PTY bytes, trimmed from the front in whole chunks. A FRESH pane (page load, or re-created after the LRU cap of 8 evicted it) received that replay at xterm's default 80×24 before its first fit. The alternate screen never reflows, so the content sat in an 80-column strip with the rest black, and nothing repaired it: the PTY was already the right size, and a same-size TIOCSWINSZ sends no SIGWINCH (measured on macOS). Once the buffer passed 1MB, the trim also dropped Claude's `?1049h` + mouse modes, so the wheel no longer reached Claude. WebGL was ruled out (forced context loss, with and without restore, repainted correctly). #397 made replays frequent: it cut every pane whenever the `/ws/agents` heartbeat went stale for 5s on a busy server.
- **Decision:** (1) **Codex is spawned inline:** `-c tui.alternate_screen="never"` on every path, including `resume --remote` (which rejects permission overrides but takes config; verified live). Its transcript then lives in xterm scrollback, the wheel scrolls it natively, nothing is sent to the agent, and a byte-log replay reproduces it faithfully. A config key rather than `--no-alt-screen`: an older Codex ignores an unknown `-c` key but refuses an unknown flag. The installed value set is pinned by the runtime-probe fixture (`codex-alt-screen-probe.json`), so a Codex that drops or renames `"never"` fails CI. (2) The server tracks the sticky DEC private modes (`agents/terminalModes.ts`: alternate screen 47/1047/1049, mouse 1000–1006/1015, focus 1004, alternate scroll 1007, bracketed paste 2004, cursor keys 1, cursor visible 25; RIS resets) with two trackers per attachment: `live` follows every chunk, `head` consumes each chunk the 1MB trim drops. A replay is `head.preamble()` + the retained bytes, which ends in exactly the live state; for Claude no_flicker that restores the alternate screen + mouse tracking after a trim. (3) For clients that ask (`?replayGeom=1`), the server sends `OSC 7777;autonomos-replay-begin;cols=C;rows=R` BEFORE the replay; the pane resizes xterm to the PTY's size first, keeps its reply-suppression window open, and re-fits to the pane after the end marker (a real size change, so the TUI gets SIGWINCH and repaints). (4) When the buffer has been trimmed and the live state is the alternate screen, the server nudges a repaint after the replay: a REAL size change and back (rows−1, restored after 60ms unless a client resized in between), rate-limited to once per 2s per PTY. (5) In acked-input mode a stale status heartbeat no longer cuts panes; per-keystroke acks already detect a dead pane socket within 1s, and every cut was a full reset + replay.
- **Rationale:** "Behave exactly like a fresh healthy pane" requires the healthy pane to be healthy. On the alternate screen it is not in xterm.js (the wheel can only become arrow keys), so Codex has to run inline, as it did before its default changed. Claude manages its own alternate screen with mouse tracking, so there the right fix is to restore exactly the modes it set and to replay at its size. Tracking only `ESC [ ?` sequences (located with indexOf) is cheap enough for 30–50 agents. Feeding the head tracker the dropped chunks makes the replay exact without keeping any history beyond the retained buffer. The geometry marker rides the existing OSC 7777 channel and is opt-in; the repaint nudge reuses the reconnect-only exception ADR-087 already allows.
- **Alternatives considered:** Restoring `?1049h`/`?1007h` for Codex: the first fix; it turns the wheel into prompt-history navigation (rejected by Terry live). A custom wheel handler that sends PageUp/PageDown to Codex on the alternate screen: depends on Codex keybindings and still has no xterm scrollback, selection or search across the transcript. `--no-alt-screen`: same effect, but an older Codex refuses the unknown flag. A headless xterm per session (`@xterm/headless` + `addon-serialize`) sending a serialized snapshot: the most robust replay for alternate-screen apps, but it parses every byte server-side for every agent; deferred until measured on the perf harness. Re-sending the same size to force a repaint: a no-op (no SIGWINCH). A bigger buffer: postpones the trim, doesn't remove it.

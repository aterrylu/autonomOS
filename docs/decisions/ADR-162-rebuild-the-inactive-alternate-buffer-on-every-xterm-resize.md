## ADR-162: Rebuild the inactive alternate buffer on every xterm resize

- **Date:** 2026-11-28
- **Decided by:** TerminalSwap@autonomOS (agent), as a bugfix under Terry's standing rule that bugfixes merge without his sign-off; assigned by TeamLead, who approved the root cause before the fix.
- **Supersedes:** part of ADR-161 (its diagnosis of the "bottom half on top" report; its fit rules stand)
- **Context:** Terry kept seeing a no_flicker Claude pane with its bottom rows at the top, until a hard refresh. He saw it on a remote server running main, which already had ADR-161. It showed up the FIRST time he switched to a pane. ADR-161 had fixed a real but different path (an unfocused window resizing xterm alone). Measured on an isolated instance (real Claude Code 2.1.332, `CLAUDE_CODE_NO_FLICKER=1`, a mock model backend, the dashboard in headless Chromium):
  - A fresh pane on a PTY sized smaller than the pane broke 6/10 and 5/12 times at zero latency, from a single client. In every broken pane the alternate buffer had `ybase` 6, `ydisp` 0 and a full 49/49 line list. Every good pane had `ybase` 0. The server saw the same resizes and repaints in good and bad runs.
  - The cause is in xterm.js 6.0.0 (unchanged in 6.1.0-beta.340). `Buffer.resize()` skips its whole adjustment block for an EMPTY buffer, including the shrink of its line list (`CircularList.maxLength`), but still records the new row count. The inactive alternate buffer is always empty, so a rows shrink while the normal buffer is active leaves it with a list sized for the OLD row count. When an app then enters the alternate screen (`?1049h`), the list isn't full, so each scroll at the bottom row grows it and does `ybase++`. That gives a scroll offset on a buffer that has no scrollback. After the next grow the list is full, the browser viewport clamps `ydisp` to 0 (its scroll range is length minus rows, which is 0), and writes land `ybase` rows below the rows that are shown. `CircularList.get()` wraps, so the bottom rows show at the top. Every later repaint goes through the same offset, which is why Claude's full ED2 redraw at the right size didn't heal it.
  - The dashboard does exactly that shrink on every first show and every reconnect. The pane fits its box (a remote link opens later than one frame), then the replay-begin marker (ADR-135) resizes xterm to the PTY's size while the normal buffer is active, and the replay's preamble enters the alternate screen. History drawn when the PTY was bigger then scrolls at the bottom row. A PTY smaller than the pane is common: another tab or device sized it last, a split or layout changed, or the agent still has its 120x40 spawn size.
  - Captured WebSocket frames of a broken pane, replayed into `@xterm/headless` 6.0.0, reproduce `ybase` 6 deterministically at the `?1049h` frame. A minimal reproducer with no agent: create a terminal at 141x49, `resize(116, 43)`, write `\x1b[?1049h`, then a 49-row frame (`row-0`…`row-48` joined by `\r\n`), then `\x1b[38;1H`, then `resize(141, 49)`. It ends with alternate `baseY` 6. A terminal created at 116x43 ends at 0.
  - Ruled out by measurement: latency or reordering between resize and output (0, 50, 150 and 400 ms all heal, because Claude answers every real SIGWINCH with ED2 and a full redraw), scroll regions (Claude's stream sets none), a reconnect storm, and a fit to a size the PTY already has. Not reproduced: `reset()` leaving queued writes in xterm's WriteBuffer.
- **Decision:** On every xterm resize, if the normal buffer is active, clear the inactive alternate buffer (`resetInactiveAltBuffer`, registered on `terminal.onResize` in `xterm-backend.ts`). `Buffer.clear()` rebuilds its line list at the current row count. It is exactly what xterm does itself on every exit from the alternate screen, and the inactive alternate buffer holds nothing, so nothing is lost. It reaches private xterm internals (`_core.buffers.alt.clear`), so it returns false when that shape is missing, and a test fails on the installed xterm if an upgrade moves it, instead of silently dropping the workaround.
- **Rationale:** `onResize` is the one point every resize passes through: fitAddon fits, the replay-begin geometry, and anything added later. So the fix doesn't depend on which caller shrank the terminal. It changes no resize timing and sends nothing to the PTY. ADR-087 (no fake resizes) and the rule against new text-channel messages both stand. Guards:
  - `xterm-backend.test.ts`: the minimal reproducer on the real xterm, plus a check that the internals are still there.
  - `e2e/terminal-replay.spec.ts` test D: a real Chromium pane fits first, then gets a smaller replay geometry and a taller replayed frame, then a full repaint at its own size. Every row must show where it was drawn.

  Both go red with the workaround removed. The e2e catches it through either assertion alone: the alternate `baseY` (18 there) or the rotated rows.
- **Alternatives considered:**
  - Drop the replay-begin resize (ADR-135): it brings back the 80-column blackout it fixed, and a user shrinking the window while an app is on the normal buffer would still hit the bug.
  - Never fit a pane before its replay: a reconnect still resets at the pane's size and shrinks to the PTY's, and any shrink outside the replay path still triggers the bug.
  - Detect the broken state and repair it (reset `ybase` plus a repaint nudge): it treats the symptom after the user sees it, and a nudge is the kind of fake resize ADR-087 removed.
  - Upgrade xterm.js: 6.1.0-beta.340 still has the bug. Reporting it upstream is Terry's call (public); the reproducer above is ready.
  - Make non-driving clients follow the PTY's size with an in-band size marker: that fixes a different, known multi-client limit (ADR-161), not this bug, and it changes multi-client behavior. Filed as a separate issue for Terry.
- **Source:** TeamLead relay of Terry's report (remote server, main with ADR-161), 2026-11-28. Fix PR `terry/terminal-half-swap-multiclient`.

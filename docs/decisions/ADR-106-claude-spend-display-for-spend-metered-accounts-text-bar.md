## ADR-106: Claude spend display for spend-metered accounts (text | % | bar), never a queue input

- **Date:** 2026-09-24
- **Who:** Terry (picked a user-selectable text / % / bar display after two design rounds; Team keeps 5h/7d only; the hard rule that spend never drives the usage queue); implementation by the UsageBars agent.
- **Context:** Anthropic's help center (retrieved 2026-09-24) says the current usage-based Enterprise plan has "no plan or seat-level usage limits": every token is billed at API rates and admins set spend limits (org / group / user). Team keeps its 5-hour and weekly windows, with optional usage credits capped monthly. Spend limits reset only with the billing period, and on a self-serve prepaid plan usage "will stop even if credits remain" until credits are bought or the limit is raised. After #387 (ADR-102), a usage-based Enterprise login rendered "no windows", which is true but tells the user nothing about the number they actually care about.
- **Decision:** (1) The server emits `spendLimit {used, limit, percent, currency, resetsAt, source, limitStatus}` ONLY when an answer has no rolling window (and the login is not Pro/Max, whose windowless answers stay a #387 diagnosis). Sources: `extra_usage` in cents (shape verified against codexbar's Enterprise fixtures; the OAuth path requires `is_enabled: true`, the session-key web body omits it) and the newer `spend` block of money objects (seen on Terry's Max payload; the shape of a SET limit is inferred, so only a money object with an integer exponent 0–4 and the same currency is accepted). The source with a readable limit wins. `limitStatus` separates `none` (no limit field) from `unreadable` (0, negative, unknown shape, mixed currency), so the UI never claims "no spend limit is set" when it merely couldn't read one. (2) The dashboard shows a per-user choice, default **text**: a gray total ("$620"), amber "$930 / $1,000" from 80%, red at or over. **%** shows the real percent (>100% over the limit); **bar** shows a fill with a red over marker. With no readable limit, % and bar fall back to the total and the tooltip says why. One floored percent drives text, color, the over marker and the tooltip, and money is truncated, so the display never claims more than is true. The choice lives in the panel's existing "Status bar display" row, which offers Text / % / Bar only for spend-metered accounts (it has no windows to act on there) and keeps "% / bar" for everyone else. The tooltip and panel carry spent / limit / %, the reset (the response's date if present and in the future, else "the next billing period"), pace (only with a known reset; UTC month math with the day clamped), and the ask-an-admin hint. (3) **Spend never drives the usage queue.** `normalizeClaudeUsage` reads only windows; tests pin that an over-limit spend neither caps a spend-only account nor changes what the queue sees for an account with windows, and a mutation feeding spend into the queue turns them red.
- **Rationale:** Dollars are the true unit of spend and work the same with or without a limit, so text is the honest default; % and bar are there for people who want the Codex-style glance. The queue exists to wait out a limit that clears on its own; a spend limit clears by an admin's action or at a billing period days or weeks away, so waiting on it would be wrong.
- **Alternatives considered:** a percentage-first default (rejected by Terry: it reads as a refilling window); ring / battery / sparkline / pace-only / threshold-only displays (design rounds 1 and 2); a "$" item for Team with credits (rejected by Terry); reusing the window toggle's values for spend (confusing, since its "text" value means percent).
- **Not verified:** a real usage-based Enterprise response (fixture from codexbar); the `spend` block's shape when a limit is set; whether Enterprise responses carry a reset date. Pace therefore appears only for the inferred `spend` source today.
- **Source:** TeamLead@autonomOS relays of Terry (2026-09-24); design rounds in the metering explainer artifact; this PR.

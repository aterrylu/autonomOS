## ADR-133: Gateway WebSocket frame limit (1 MiB) and per-socket warning budget

- **Date:** 2026-09-30
- **Decided by:** TeamLead assigned the follow-ups from SecurityAudit-Claude's review of ADR-127 (V6); SecurityFix-Hardening (agent) chose the limits.
- **Context:** ADR-127 validated every `/ws/gateway` frame and bounded each logged field, and the review left three items open. First, `@hono/node-ws` 1.3.x builds its WebSocketServer with `ws`'s default 100 MiB `maxPayload` and takes no options, so any agent could make the server buffer and parse up to 100 MiB per frame. Second, one line per malformed frame let a single client churn the rotating log. Third, two pre-existing log lines interpolated client-supplied values raw: a rejected register's session id and a failed route's destination. A newline in either could forge a log line.
- **Decision:**
  1. The internal app's WebSocketServer, which serves only `/ws/gateway`, gets `maxPayload = MAX_GATEWAY_FRAME_BYTES` (1 MiB, in `gateway/deliveryTimings.ts`). `createNodeWebSocket` returns its `wss`, and `ws` reads `options.maxPayload` when each upgrade completes, so no dependency patch is needed. An over-limit frame closes that socket with 1009.
  2. The channel server's `send` tool checks the whole frame's byte size against the same constant before sending, and answers an oversized message with a clear error ("too large … put the content in a file and send its path"). Otherwise the gateway's 1009 close gives no reply, and the sender would wait out its request deadline and see what looks like a lost message. The constant is shared across the bundle boundary the same way the delivery timings are.
  3. Malformed-frame and unknown-type warnings go through a per-socket token bucket: 5, refilled one per 12 s. Withheld warnings are counted and reported on the next allowed line and in a summary when the socket closes.
  4. Client-supplied values in log lines go through `logField`: quoted (JSON) and capped at 64 characters with a `…(+N chars)` marker.
- **Rationale:** 1 MiB is two orders of magnitude below the default and far above any realistic agent message; a longer payload belongs in a file whose path is sent. Checking on the sender's side turns the only visible effect of the limit into a clear, immediate error rather than a timeout. The budget bounds how many lines one client can produce without hiding that it happened, since the counts are logged. Quoting fixes log injection at the formatting boundary rather than by trusting the schema to have excluded every control character.
- **Alternatives considered:** (a) Patch `@hono/node-ws` (patchedDependencies) or upstream an options pass-through. Unnecessary: the returned `wss` can be configured, which survives upgrades of that package as long as it keeps returning it (the test pins the 1009 behaviour). (b) A pre-parse length check in the route. Rejected: by then `ws` has already buffered the whole frame, so it doesn't bound memory. (c) The same limit on the PUBLIC app's WebSockets (terminal, agents). Not now: a user pasting a large block into a terminal would be cut, and those sockets are operator-authenticated; that is a separate decision. (d) A global (not per-socket) warning budget. Rejected: one noisy client could silence warnings about every other client.
- **Source:** SecurityAudit-Claude's review of PR #444 (V6); follow-up plan `~/.claude/plans/gateway-ws-hardening-followups.md`; PR for `terry/gateway-ws-limits`.

## What It Is

ComposioHQ's agent-orchestrator is a multi-agent framework where **the orchestrating intelligence is itself an LLM agent**, not hardcoded routing logic. The orchestrator agent receives a high-level goal and dynamically decides how to break it down, which specialist agents to invoke, and when the goal is complete.

The meta-story: the framework was substantially built by running the framework on itself — agents writing agents. This is a proof-of-concept for agentic software development.

## Architecture

```
User Goal
    │
    ▼
┌─────────────────────────────────────────┐
│  Orchestrator Agent (Claude)            │
│  - receives goal                        │
│  - decides which agents to call         │
│  - synthesizes results                  │
│  - decides when goal is achieved        │
└────────┬────────────────────────────────┘
         │ calls (via Composio tool integration)
    ┌────┴─────────────────────────────────────┐
    │           Plugin Slots (8 max)           │
    │                                          │
    │  [Researcher] [Writer] [Code] [Browser]  │
    │  [Memory]     [Email]  [Cal]  [Custom]   │
    └──────────────────────────────────────────┘
```

### Plugin Slot System

The orchestrator has exactly 8 plugin slots. Each slot is a specialist agent or tool integration:
- **Fixed slots**: Researcher, Writer, Code, Browser (always available)
- **Configurable slots**: Memory, Email, Calendar, Custom (user-configurable)

The 8-slot limit is intentional — forces composability over sprawl. You can't add a 9th agent; you must decide what to replace.

Each plugin exposes a typed interface to the orchestrator:
```typescript
interface Plugin {
  name: string
  description: string   // what the orchestrator sees
  capabilities: string[]
  execute(task: Task): Promise<Result>
}
```

The orchestrator's system prompt includes all plugin descriptions. It calls them by name in its tool calls.

## Orchestration via LLM

The orchestrator is not a rule engine. It's a Claude instance with a specialized system prompt that includes:
- Goal decomposition strategies
- When to use each plugin
- How to synthesize partial results
- Failure and retry patterns

No code determines routing logic. The LLM decides. This means:
- **Flexible**: handles novel tasks that don't fit predetermined flows
- **Unpredictable**: can make unexpected choices
- **Expensive**: orchestrator uses many tokens (it reasons in detail)

## "Built by Itself" Mechanism

The meta-story of construction:
1. Human wrote the initial orchestrator shell (minimal system prompt + plugin loader)
2. Ran the orchestrator with goal: "Implement the Code plugin with these specs"
3. Code plugin was generated by the orchestrator
4. Ran again: "Implement the Memory plugin"
5. Memory plugin generated
6. Eventually: "Write the test suite for the orchestrator"

This is documented in their blog and repo. The agents wrote approximately 60% of the codebase by this method, with humans reviewing and occasionally correcting.

## What Makes It Interesting

1. **LLM as orchestrator** — the orchestrator being an LLM rather than code is legitimately more flexible. It can handle edge cases that rules can't anticipate.

2. **8-slot constraint** — arbitrary but effective. Forces architectural discipline. "You can have 8 plugins, choose wisely."

3. **Built by itself** — strong validation of the agentic development thesis. If agents can build orchestration frameworks, the orchestration model is sound enough for complex work.

4. **Composio as infrastructure** — offloading tool auth/integration to a dedicated service is the right separation of concerns for complex tool use.

---

## Weaknesses

- **Orchestrator is expensive** — LLM reasoning on every decision. Cost scales linearly with task complexity.
- **Unpredictable routing** — no guarantee of which plugin gets called. Hard to reason about in advance.
- **8-slot rigidity** — if you need 9 capabilities, you're stuck. Workaround: nest orchestrators (orchestrator of orchestrators).
- **Composio coupling** — the tool integration layer depends on Composio's commercial service. Self-hosting is complex.
- **No scheduling** — goal-triggered, not cron-based.
- **No persistent sessions** — each goal is a fresh orchestration run.

### Key borrowings

- **LLM-as-orchestrator** — when autonomOS builds multi-agent support, the orchestrator itself should be a Claude agent. Don't hardcode routing logic. Let an orchestrator agent read goals and decide which worker agents to invoke. This aligns with our "everything is an agent" philosophy.

- **Typed plugin interfaces** — even without 8-slot constraints, every autonomOS agent should expose a typed interface (its YAML schema) that other agents can call. `name`, `description`, `capabilities` are the minimum.

- **Composio pattern for tools** — MCP servers are autonomOS's Composio. The pattern of "tool integration as a separate concern from orchestration" is correct. autonomOS agents should get capabilities via MCP, not by bundling tool code.

- **"Built by itself" as a goal** — this is autonomOS's long-term north star. Agents that build and configure other agents. The orchestrator-agent pattern makes this tractable.
